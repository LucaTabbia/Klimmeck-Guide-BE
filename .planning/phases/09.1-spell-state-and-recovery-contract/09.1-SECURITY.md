## Trust Boundaries

| Boundary | Descrizione | Dati |
|----------|-------------|------|
| client -> `equipSpell` / `unequipSpell` / `useSpell` | ownership per `@OwnsCharacter` invariata; gli usi e gli istanti non arrivano mai dal client | id personaggio, id magia |
| client -> `character` / `characterUpdated` | lo stato delle magie segue l'autorizzazione esistente; orfani scartati dal mapper | `spellStates`, `activeSpells` |
| Redis (Bull) -> processor | dati del job non fidati, at-least-once, job anticipati; il job e solo un trigger, decide il DB | `characterId`, `spellId`, `dueAt` |
| timer -> DB (sweep) | single-flight, in serie, solo personaggi attivi, stop pulito | stati con istanti scaduti |
| processo -> DB (migrazione al boot e `migrateOne`) | pipeline idempotente, archiviati esclusi, mai bloccante | `status.spellStates`, mirror |
| catalogo a DB (scritto a mano) -> regole | `maxUsages`/`recoveryTime` malformati tollerati: la magia non recupera o non si equipaggia, mai un errore sul filo | catalogo magie |
| servizio / outcome writer -> Redis | accodamento best-effort con timeout, mai nella risposta del filo | job `recover` |
| env -> boot | `SPELL_RECOVERY_SWEEP_INTERVAL_MS` validata, messaggio senza valore | configurazione |
| documentazione / CI -> branch | handoff e invarianti proteggono contratto e whitelist | BACKEND-NOTES, `schema.gql` |

## Observations (senza id di minaccia)

- Una voce di stato scritta a mano con `usages` assente o non intero resta com'e nel DB (scelta WR-03, nessun uso regalato): se arrivasse sul filo, `SpellState.usages: Int!` darebbe un errore GraphQL su quel personaggio. Nessuno scrittore del BE la produce; verifica di hardening segnalata per la Phase 10 (nota di follow-up di 09.1-REVIEW-FIX).
- I percorsi che non passano dal mapper (`characters` dell'innkeeper e `User.currentCharacter`) restano non popolati per `spellStates`: documentato in BACKEND-NOTES (Pitfall 4, «non selezionare `spellStates` su quei percorsi»), nessuna esposizione di dati altrui.
- Con `SPELL_RECOVERY_SWEEP_INTERVAL_MS=0` non resta alcuna rete di sicurezza fino al boot successivo: documentato in §8, in produzione tenere lo sweep attivo; Redis `maxmemory-policy` da verificare (consigliata `noeviction`).
- Il set dei WARN per magie non accreditabili e limitato a 1 000 coppie (`spell-recovery.service.ts:21,120-123`, la piu vecchia esce); l'indice su `status.spellStates.recoveries` e rinviato alla Phase 10.
- Il diff di `.env.example` include le due righe `SIGHTENGINE_*` con valore vuoto (solo nomi): nessun segreto, ma sono estranee alla fase.
