# Phase 9.1: Code Review Report

**Reviewed:** 2026-10-27T14:45:00Z

## Summary

The phase is solid. The credit is a single conditional update (`dueCreditFilter` + `$inc`/`$pop` + mirror with `arrayFilters` on both ref forms), idempotent under replay and under the processor/sweep race, with no read-modify-write and no use of the server clock inside pipelines. Update pipelines use `$arrayElemAt` + `$let` (MongoDB 4.2 compatible). The outcome plan copies before mutating, takes `min(requested, usages)`, keeps duplicate instants and relies on the transaction snapshot (reads in session) so a concurrent credit surfaces as a `WriteConflict` and restarts the transaction instead of being overwritten. The wire mapper drops orphans, keeps slot order and falls back to the mirror only when the state entry is missing. Queue data is validated as untrusted, logs carry ids and error codes only, `describeError` is used throughout, the removed recovery-unavailable code leaves no residue in `src`/`test`, and `npx eslint` on the touched production files reports only the 11 known warnings on untouched lines of `characters.service.ts`; `tsc -p tsconfig.build.json` is clean.

No critical issues. Three warnings concern operational edge cases of the recovery path (an early job swallowed with the sweep off, a permanent per-sweep warning for states whose spell left the catalog, a trim pipeline that does not guard malformed entries). Five info items cover coupling, a fallback hole, duplicate-handling, a misleading message and a documented schema hazard.

Overlap boot migration vs first sweep: safe. Every credit calls `migrateOne` first (idempotent per-character repair pipeline), the sweep only selects characters that already have `recoveries`, and each repair/credit is atomic on a single document. Sweeper single-flight and shutdown are correct (`stopping` flag, `inFlight` awaited with a swallowed rejection, unref'd timer).

## Warnings

### WR-01: A job that fires early is swallowed; with the sweep off the usage is not credited until the next boot

**File:** `src/characters/spells/spell-recovery.processor.ts:42-47`
**Issue:** When `dueAt > now` the processor logs and returns, so Bull marks the job completed and (with `removeOnComplete: true`) deletes it. The only remaining safety net is the sweep. Bull computes the delay against the Redis clock while the check uses the application `Clock`; a few milliseconds of skew (or a delayed-set promotion slightly ahead of the app clock) makes this path reachable in normal operation, not only in tests. With the default 60 s interval the player waits up to a minute extra. With `SPELL_RECOVERY_SWEEP_INTERVAL_MS=0` (documented as "off") the usage is never credited until the next boot reconciler. The contract says the sweep "covers" early jobs, but the documented off switch removes that coverage.
**Fix:** Either make the early job retry itself, or tolerate a small skew. For example, throw a dedicated error so Bull retries with backoff, or re-enqueue the same deterministic `jobId` with `delay = dueAt - now` through `enqueueTrigger` (best-effort) before returning:
```ts
if (trigger.dueAt.getTime() > this.clock.now().getTime()) {
    await enqueueTrigger(this.queue, spellRecoveryTrigger(
        trigger.characterId, trigger.spellId, trigger.dueAt), context);
    return;
}
```
Alternatively document in `.env.example` and `BACKEND-NOTES.md` that `0` also disables the early-job fallback.

### WR-02: A state whose spell left the catalog is retried and warned about on every sweep, forever

**File:** `src/characters/spells/spell-recovery.service.ts:83-97` (called from `recoverDue`, `recoverLegacy`); `src/characters/spells/spell-recovery.sweeper.ts:76-96`
**Issue:** If a catalog spell is deleted (or its `maxUsages` is malformed) while a character holds a due instant in `status.spellStates`, `maxUsagesOf` returns `null` and logs a WARN, but the instant is never consumed. The sweeper's `find` selects that character on every tick, so the same WARN is emitted every interval per affected state (default: every minute) and the same lookups are repeated indefinitely. The wire mapper already hides such entries from the client, so nothing ever resolves them. The message also says "assente dal catalogo" even when the spell exists with an invalid `maxUsages`.
**Fix:** Log once per `(spellId)` per process (a `Set<string>` of already-reported ids in the service), or downgrade to `debug` after the first report. Optionally have the migrator drop `spellStates` entries (and `recoveries`) of spells missing from the catalog, as `status.spells` orphans already are for the wire. Differentiate the message: "assente dal catalogo" versus "maxUsages non valido".

### WR-03: The out-of-range filter and the trim pipeline do not guard malformed entries, and the JS twin does

**File:** `src/characters/spells/spell-state.migration.ts:190-236` (`outOfRangeFilter`), `239-294` (`spellStatesTrimPipeline`); compare `src/characters/spells/spell-state.migrator.ts:170-181` (`isOutOfRange`)
**Issue:** `isOutOfRange` returns `false` when `usages` is not a number, but the Mongo predicate has no such guard. For an entry with a missing or non-numeric `usages` (the `required` flag is not enforced on raw writes), `MISSING_USAGES` evaluates to null; `$gt: [size, null]` is then true, so the character matches `outOfRangeFilter` and the trim pipeline reaches `$slice` with a null count. Depending on the server this either errors or yields a null `recoveries`. A pipeline error inside `updateMany` aborts the remaining documents, so one corrupt state could stop trims for the whole batch on every boot (`migrateAll` only logs it) and make `migrateOne` throw for that character. A non-array `recoveries` makes `$size` throw in the same way. The probability is low (data is written only through guarded updates), but the failure mode is wide, and the intent to ignore such entries is already encoded in the JS twin. (Confidence on the exact server behavior for the null `$slice` count is moderate: please confirm with a probe in the migrator int-spec.)
**Fix:** Guard both pipelines with the same preconditions as the JS predicate, for example in `outOfRangeFilter` and the trim `$cond`:
```ts
{ $isNumber: '$$state.usages' },
{ $eq: [{ $type: '$$state.recoveries' }, 'array'] },
```
and add a migrator int-spec case with a state missing `usages` asserting that `migrateAll` completes and other characters are still trimmed.

## Info

### IN-01: `isUsageCount` lives in an injectable module file and is imported across domains

**File:** `src/characters/spells/spell-state.migrator.ts:166`; imported by `src/characters/spells/spell-recovery.service.ts:10` and `src/quests/outcomes/resolution-loader.service.ts:5`
**Issue:** A pure predicate is exported from the Nest provider that owns Mongoose models. The quests loader now depends on the migrator module (and transitively on its model and migration imports) only for a one-line check, which couples the outcomes domain to the boot migration.
**Fix:** Move `isUsageCount` to `spell-state.snapshot.ts` (already the home of pure spell-state helpers) and import it from there in all three places.

### IN-02: `equipSpell` can write a null mirror usage when the state entry is missing and the catalog `maxUsages` is malformed

**File:** `src/characters/characters.service.ts:254`, `src/characters/spells/active-spell.updates.ts:33-70`
**Issue:** `equipSpellUpdate(spellId, spell.maxUsages)` passes the raw catalog value (typed `number`, not validated). If the state entry is absent (unmigrated or repaired later) and `maxUsages` is `undefined`, the pipeline `$ifNull` fallback serializes to null and the slot is created with `usages: null`, which then fails the consistency expression and `ActiveSpell.usages: Int!` on the wire. Every other reader (migrator, credit, loader) validates with `isUsageCount`.
**Fix:** In `equipSpell`, reject non-`isUsageCount` values with the existing `ResourceNotFoundException.spell()` (as `useSpell` does for `recoveryTime`) before building the update.

### IN-03: The repair pipeline does not deduplicate `status.spells`

**File:** `src/characters/spells/spell-state.migration.ts:25-42` (`KNOWN`), `106-143`
**Issue:** If `status.spells` ever contains the same id twice (pre-existing data), the repair creates two state entries; `$[s]` array filters then credit both and the consistency check treats the duplicate as valid. The learn path guards against it, so this only concerns legacy data.
**Fix:** Deduplicate `KNOWN` (for example with `$reduce` over a `$setUnion`-free accumulator, keeping 4.2 compatibility) or log a WARN in the verifier when `status.spells` has duplicates.

### IN-04: `isOutOfRange` duplicates the Mongo predicate

**File:** `src/characters/spells/spell-state.migrator.ts:170-181` and `src/characters/spells/spell-state.migration.ts:190-236`
**Issue:** The WARN decision is made in JavaScript while the trim is decided in Mongo; the two already differ (see WR-03), so the warning can disagree with what is actually trimmed.
**Fix:** Keep one definition (for example warn from the documents returned by the same filter and assert in the spec that both predicates agree on a table of cases).

### IN-05: `spellStates { spell }` is not selectable on the paths that bypass the mapper

**File:** `src/models/character/character-status.model.ts:51-54`, `src/models/character/spell-state.model.ts:8-12`
**Issue:** Documented as Pitfall 4 and in the handoff, but the schema still exposes `spellStates` with a non-null `spell` on `characters` (innkeeper) and `User.currentCharacter`, where the field is an unpopulated ObjectId and resolves to a GraphQL error. Nothing in the SDL tells a client which paths are safe.
**Fix:** Optional: add a `description` to the `spellStates` field stating that it is populated only on `character` and `characterUpdated`, or route those two read paths through the mapper in a later phase.
