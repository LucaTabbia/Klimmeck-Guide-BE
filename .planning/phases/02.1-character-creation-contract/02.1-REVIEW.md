## Warnings

### WR-01: I limiti di lunghezza contano solo i grafemi: un nome di 2 "caratteri" o un background di 500 può pesare decine di KB

**File:** `src/characters/creation/character-name.ts:19-27`, `src/characters/creation/create-character-input.validator.ts:38-44` (con `src/characters/creation/grapheme-count.ts:6-8`)

**Issue:** `countGraphemes` segue UAX #29, per cui una sequenza arbitrariamente lunga di code point può formare un **solo** grapheme cluster. Due casi concreti, verificati con Node 22:

- **Nome.** Lo jamo hangul U+1100 è `\p{Lo}` e la regola GB6 non spezza mai `L × L`: `'ᄀ'.repeat(5000) + 'a'` ha 5001 unità UTF-16, conta **2 grafemi**, supera `ALLOWED_NAME_CHARACTERS` e `ANY_LETTER` → `isValidCharacterName` restituisce `true`. Il regex esclude `\p{M}` ma non protegge da questo caso perché i jamo sono lettere.
- **Background.** `'a' + '́'.repeat(5000)` conta **1 grafema**: 500 di questi "caratteri" superano il controllo con qualunque dimensione.

L'unico tetto rimasto è il body limit HTTP (≈100 KB di default). Il risultato è un `infos.name` o `infos.background` di decine di KB persistito, indicizzato (il nome entra nella chiave dell'indice unico) e poi servito a ogni client che carica il personaggio o la lista `characters`. Non è un rischio di integrità, ma è un vettore di garbage/DoS leggero e rompe il contratto "2–20 caratteri" / "≤ 500 caratteri" nello spirito di D-05 e D-07.

**Fix:** affiancare al conteggio dei grafemi un tetto rigido sulle unità UTF-16. Per il nome, dato che il regex vieta i segni combinanti, una lettera legittima occupa al più una coppia surrogata: `2 × 20` è un limite che non respinge nessun nome reale. Per il background una sequenza emoji ZWJ vale ~11 unità, quindi `8 ×` è generoso ma finito.

```ts
// character-name.ts
export const CHARACTER_NAME_MAX_CODE_UNITS = CHARACTER_NAME_MAX_LENGTH * 2;

export function isValidCharacterName(normalized: string): boolean {
    if (normalized.length > CHARACTER_NAME_MAX_CODE_UNITS) return false;
    const length = countGraphemes(normalized);
    // ... resto invariato
}

// create-character-input.validator.ts
export const BACKGROUND_MAX_CODE_UNITS = BACKGROUND_MAX_GRAPHEMES * 8;

function normalizeBackground(raw: string | null | undefined): string {
    const background = (raw ?? '').trim();
    if (
        background.length > BACKGROUND_MAX_CODE_UNITS ||
        countGraphemes(background) > BACKGROUND_MAX_GRAPHEMES
    ) {
        throw CharacterCreationException.backgroundTooLong();
    }
    return background;
}
```

Test da aggiungere (red prima del fix): `isValidCharacterName('ᄀ'.repeat(100) + 'a')` → `false`; `validateCreateCharacterInput({ ...VALID, background: 'a' + '́'.repeat(5000) })` → `BAD_USER_INPUT`. In alternativa, per il solo nome, contare i code point (`[...normalized].length`) invece dei grafemi: con `\p{M}` già vietato, per ogni input legittimo coincidono.

### WR-02: Le lettere modificatrici (`\p{Lm}`) soddisfano la regola "almeno una lettera" di D-19 e aggirano la normalizzazione dell'apostrofo

**File:** `src/characters/creation/character-name.ts:7-8` (regex) e `:14` (normalizzazione)

**Issue:** `\p{L}` include la categoria `Lm` (modifier letters), che contiene simboli visivamente identici a punteggiatura: U+02BC `ʼ` (modifier letter apostrophe), U+02BB `ʻ`, U+02C8 `ˈ`/U+02CC `ˌ` (primi), U+0640 `ـ` (tatweel arabo, rende come una linea). Verificato: `"ʼʼ"`, `"ˈˌ"` e `"ـــ"` passano `isValidCharacterName` → nomi "solo punteggiatura" accettati, contro D-19 che li vuole respinti con `CHARACTER_NAME_INVALID`. Inoltre `"DʼArcy"` (U+02BC) passa e non viene normalizzato in `"D'Arcy"`: la collation a strength 2 lo considera un nome **diverso**, quindi convive con `"D'Arcy"` come quasi-duplicato visivamente indistinguibile, esattamente il caso che D-19 vuole far collidere.

**Fix:** normalizzare anche gli apostrofi "lettera" e richiedere almeno una lettera di base (non modificatrice). Mantenere `\p{L}` nella classe ammessa evita di respingere lettere `Lm` legittime (es. ʻokina hawaiano, ー giapponese), ma la regola "almeno una lettera" deve guardare solo `Lu/Ll/Lt/Lo`.

```ts
const APOSTROPHE_LOOKALIKES = /[’ʼʻ]/g; // ’ ʼ ʻ
const ANY_BASE_LETTER = /[\p{Lu}\p{Ll}\p{Lt}\p{Lo}]/u;

export function normalizeCharacterName(raw: string): string {
    return raw
        .normalize('NFC')
        .replace(APOSTROPHE_LOOKALIKES, "'")
        .trim()
        .replace(WHITESPACE_RUN, ' ');
}

// in isValidCharacterName: ANY_BASE_LETTER.test(normalized) al posto di ANY_LETTER
```

Test da aggiungere: `normalizeCharacterName('DʼArcy')` → `"D'Arcy"`; `isValidCharacterName('ʼʼ')`, `('ـــ')` → `false`. Se si preferisce la linea dura, escludere `\p{Lm}` anche dalla classe ammessa (`[\p{Lu}\p{Ll}\p{Lt}\p{Lo}' -]`), accettando di respingere i nomi hawaiani con ʻokina.

### WR-03: Un utente inesistente riceve `CHARACTER_ALREADY_EXISTS`: il claim conflaziona "documento mancante" e "ha già un personaggio"

**File:** `src/characters/creation/character-creation.service.ts:55-62`

**Issue:** `findOneAndUpdate({ _id: userId, currentCharacter: null })` restituisce `null` sia quando `currentCharacter` è già valorizzato sia quando **lo User non esiste**. `AuthGuard` → `AuthIdentityResolver.resolveBearer` → `AccessTokenService.verify` controlla solo firma, audience e claims del JWT: non interroga il DB. Esiste la mutation `deleteUser`. Scenario: un utente cancellato (o un DB ripristinato) con un access token ancora valido (≤ 15 min) chiama `createCharacter` e riceve "Hai già un personaggio". Il FE, su `CHARACTER_ALREADY_EXISTS`, ragionevolmente ricarica `me` per entrare in gioco, che però risponde `NOT_FOUND`: l'utente resta bloccato su un messaggio falso, e nei log il caso è indistinguibile da un vero doppio personaggio.

**Fix:** dopo un claim nullo, distinguere i due casi con una lettura nella stessa sessione. L'errore più coerente per il FE è `UNAUTHENTICATED` (il bearer punta a un utente che non c'è più, l'app sa già rimandare al login):

```ts
if (!claimed) throw await this.rejectUnclaimed(userId, session);

private async rejectUnclaimed(
    userId: Types.ObjectId,
    session: ClientSession,
): Promise<Error> {
    const exists = await this.userModel.exists({ _id: userId }).session(session);
    return exists
        ? CharacterCreationException.alreadyExists()
        : AuthException.unauthenticated();
}
```

Se si preferisce non far dipendere il modulo da `AuthException`, `new NotFoundException(\`User with id ${userId.toHexString()} not found\`)` è l'alternativa coerente con `UsersService.findOne`. Test di integrazione: cancellare lo User dopo `createAuthenticatedUser`, chiamare la mutation con il bearer ancora valido e asserire il codice scelto e `countDocuments() === 0`.

### IN-01: `AuthException` e `CharacterCreationException` duplicano la stessa forma di "HttpException con codice"

**File:** `src/characters/creation/character-creation.exception.ts:4-13`, `src/auth/auth.exception.ts:4-13`, `src/graphql/format-domain-error.ts:8,35-41`

**Issue:** Le due classi hanno lo stesso costruttore privato (`super({ statusCode, error, message, code })`, `this.code`, `this.extensions = { code }`) e lo stesso commento. `formatDomainError` le riconosce con un duck-typing strutturale (`CodedHttpException` come intersezione di tipi + controllo `typeof extensions.code === 'string'`). Alla terza famiglia di codici (Phase 3, ruoli) la duplicazione cresce.

**Fix:** estrarre `src/graphql/coded-http.exception.ts` con `abstract class CodedHttpException<C extends string> extends HttpException` che riceve status, label e codice e imposta `code`/`extensions`; le due sottoclassi ereditano e tengono solo le factory. Il formatter diventa `error instanceof CodedHttpException`, eliminando il cast strutturale.

### IN-03: I messaggi utente cablano 2, 20 e 500 mentre esistono le costanti

### IN-04: Il fallback di `formatDomainError` sul body Nest è limitato ai codici auth

**File:** `src/graphql/format-domain-error.ts:6,32,43-53`

**Issue:** Il formatter si chiama "domain" ma `readNestBodyAuthCode` ripristina il codice dal body solo se appartiene a `AuthErrorCode`; un `CHARACTER_*` che arrivasse per quella via (errore non tracciabile con `unwrapResolverError`) resterebbe `BAD_REQUEST`. Oggi non succede perché le `CharacterCreationException` nascono nel resolver e vengono riconosciute per istanza (test wire verdi), quindi è solo un'asimmetria concettuale, blindata dal test "keeps the body fallback limited to auth error codes".

**Fix:** o rendere il fallback generico (whitelist = unione di tutti gli enum di codici di dominio, es. `DOMAIN_ERROR_CODES = [...Object.values(AuthErrorCode), ...Object.values(CharacterCreationErrorCode)]`), o documentare nel commento che il fallback esiste solo per gli errori lanciati dalla guard (fuori dal resolver) e che ogni nuova famiglia di codici deve viaggiare come istanza. Con IN-01 risolta il fallback può probabilmente sparire.

### IN-05: Il nome accetta punteggiatura in testa, in coda e consecutiva

**File:** `src/characters/creation/character-name.ts:7`

**Issue:** `^[\p{L}' -]+$` più "almeno una lettera" accetta `"- a"`, `"'Aria"`, `"Aria-"`, `"A--B"`, `"A''B"`. Non viola D-05 alla lettera, ma produce nomi che la UI mostrerà come sbavature e che l'utente non sceglierebbe consapevolmente.

**Fix:** se si vuole stringere, richiedere lettera iniziale e finale e vietare punteggiatura doppia: `/^\p{L}(?:[' -]?\p{L})*$/u` (dopo WR-02, con la classe lettere scelta). Decisione di prodotto: da confermare con il FE, che replica la regola per la validazione live.

### IN-06: L'esclusione di `\p{M}` respinge le scritture che richiedono segni combinanti

**File:** `src/characters/creation/character-name.ts:7,10`

**Issue:** Dopo NFC le lettere latine accentate sono precomposte, ma devanagari (`राम` = र + ा U+093E `Mc` + म), thai, hebrew con niqqud e arabo con diacritici restano fatti di segni `\p{M}` e vengono respinti con `CHARACTER_NAME_INVALID`. Coerente con D-05 ("solo `\p{L}`") e accettabile per il pubblico del canale, ma è un limite che il FE e la UAT devono conoscere.

**Fix:** registrare il limite in `BACKEND-NOTES.md` §nome ("solo lettere precomposte: scritture con segni combinanti non supportate") oppure, se si vuole supportarle, ammettere `\p{M}` **solo** dopo una lettera (`/^(?:\p{L}\p{M}*)(?:[' -]?\p{L}\p{M}*)*$/u`) tenendo WR-01 come tetto contro lo Zalgo.

### IN-07: `CityDocument` e `PointOfInterestDocument` usano il `Document` del DOM, e il nuovo servizio tipizza i due modelli in modo diverso

**File:** `src/characters/creation/starting-location.service.ts:19-21`, `src/models/city.model.ts:41`, `src/models/point-of-interest.model.ts:31`

**Issue:** Entrambi i file modello importano solo `Types` da `mongoose`, quindi `City & Document` e `PointOfInterest & Document` risolvono al `Document` **del DOM** (lib di default per `target: esnext`). Compila per caso. Il nuovo codice lo rivela: `Model<CityDocument>` per le città e `Model<PointOfInterest>` (senza Document) per i POI, nello stesso costruttore. Pre-esistente, ma la fase introduce i primi consumer tipizzati di questi alias.

**Fix:** nei due modelli `import { Document, Types } from 'mongoose'` (come fanno `user.model.ts` e `character.model.ts`); poi in `StartingLocationService` usare `Model<PointOfInterestDocument>` per coerenza. Boy Scout a basso rischio, da verificare con `npx tsc --noEmit`.
