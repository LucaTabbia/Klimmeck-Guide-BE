## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Contract
- **D-01:** Mutation **`createCharacter(input: CreateCharacterInput!): User!`**. Identity comes only from `@CurrentUser()` (BE-AUTH-06): no `userId`/`twitchId` in the input. Returns the updated `User` with `currentCharacter` populated (same shape the `me` query returns), so the app can swap its session user without a second round trip.
- **D-02:** Input fields: `name: String!`, `sex`, `pronoun`, `race`, `classType` (the existing TS enums `SexType`, `PronounType`, `RaceType`, `ClassType`), `age: Int!`, `background: String` (optional), `imagePath: String` (optional URL). Exposing the four enums as registered GraphQL enum types (they are already `registerEnumType`'d) is preferred over `String`: the app sends `enum.name` strings either way.
- **D-03:** **One character per user, atomic.** The `currentCharacter` assignment is a conditional update (`findOneAndUpdate({ _id, currentCharacter: null }, …)`); a user who already has a character — including the loser of two concurrent calls — gets `CHARACTER_ALREADY_EXISTS` and **no partial document remains** (transaction on the replica set, or compensating delete of the just-created character: planner's choice, both covered by an integration test).
- **D-04:** Stable error codes in `errors[0].extensions.code`, following the Phase 2 pattern (typed `GraphQLError` subclasses): `CHARACTER_NAME_INVALID`, `CHARACTER_NAME_TAKEN`, `CHARACTER_AGE_OUT_OF_RANGE`, `CHARACTER_ALREADY_EXISTS`, `STARTING_LOCATION_UNAVAILABLE`; enum/length violations the GraphQL layer does not already reject use the generic validation code (`BAD_USER_INPUT`). Messages are Italian and user-facing; codes never change.

#### Validation (authoritative — the app's live validation is UX only)
- **D-05:** **Name:** trimmed, internal whitespace collapsed to single spaces, 2–20 characters, only Unicode letters (`\p{L}`), spaces, apostrophes (`'` and `’`) and hyphens; **unique case-insensitive** across all characters. Uniqueness is enforced by the database (unique index on a normalized key such as `infos.nameKey`, or a case-insensitive collation index) and `E11000` maps to `CHARACTER_NAME_TAKEN`. Existing characters without the key need a one-off backfill or a lazily-computed key — planner decides.
- **D-06:** **Age by race** — single source of truth, a TypeScript constant module (e.g. `src/characters/race-traits.ts`) used by both the validator and the `raceTraits` query. Table **aligned to the lore** (accepted by the user on 2026-10-09; supersedes the D&D-inspired table first proposed in the FE discuss):

  | race | minAge | maxAge | lore |
  |---|---|---|---|
  | human | 16 | 200 | 60–70 normally, mages beyond 200 |
  | elf | 100 | 9999 | infinite life, >1000 common |
  | halfelf | 16 | 130 | 120–130 |
  | dwarf | 40 | 140 | 130–140 |
  | gnome | 16 | 60 | ~60 |
  | halfling | 16 | 70 | ~70 |
  | dragonborn | 16 | 180 | 150–180 |
  | tiefling | 16 | 120 | 100–120 |
  | aarakocra | 3 | 40 | 30–40 |

- **D-07:** **Background:** optional, ≤ 500 characters after trim. Absent/blank is stored as the empty string (`infos.background` stays `String!` in the schema — no breaking change for existing consumers).
- **D-08:** **imagePath:** optional; when present it must be an `https` URL (light check: the Cloudinary secure URL returned by `POST /cloudinary/uploadImage`, folder `characters_profile`). **No NSFW moderation in this phase** (user decision 2026-10-08); recorded as BE-HARD debt.

#### Starting state (backend-owned)
- **D-09:** `status`: `level 1`, `title rookie`, `xp 0` (→ `maxActiveSpells` virtual = 0, spells unlock later by design), `currentLifePoints 100`, `maxLifePoints 100`, `coins { gold 0, silver 5, copper 0 }` (user: "5 monete di argento"), `injuries []`, `spells []`. `quests`: `completedQuests []`, `pendingQuest null`. `assets`: `ownedEquipments []`, `ownedItems []`, `wearedEquipment {}`, `activeSpells []`, `pet null`. No boot-time check (data may legitimately be seeded later), but a WARN log at startup for missing home cities is welcome.

## Summary

Il contratto si costruisce quasi tutto con quello che c'è già: `@CurrentUser()` / `AuthIdentity`, `UsersService.findOne` (populate di `currentCharacter`), gli enum già registrati, il replica set di test (transazioni disponibili) e `createAuthTestApp`. Gli esperimenti hanno però trovato **tre fatti che cambiano il piano** rispetto a quanto scritto nel CONTEXT.

1. **Il "pattern Phase 2" non è una sottoclasse di `GraphQLError`.** `AuthException` estende `UnauthorizedException` (HttpException) con `extensions = { code }`, e il codice arriva sul wire solo grazie a `formatAuthError`. Il driver Apollo di Nest riscrive il codice di ogni HttpException, e `formatAuthError` ripristina solo gli `AuthErrorCode`. Verificato sul wire: una `BadRequestException` con `extensions.code = CHARACTER_AGE_OUT_OF_RANGE` arriva come `code: "BAD_REQUEST"` e in più espone `originalError`. Una vera sottoclasse di `GraphQLError` porta il codice giusto, ma Nest la registra come `ERROR [ExceptionsHandler]` con stack trace a ogni errore di validazione. → Serve una `CharacterCreationException extends BadRequestException` più un **formatter generalizzato** a ogni HttpException che porta `extensions.code`.
2. **I riferimenti ObjectId dei modelli sono `Mixed`** (verificato: `User.currentCharacter`, `Character.status.location`, `City.markerLocation`). Mongoose non fa cast: un id passato come stringa viene salvato come stringa. Il `$set` di `currentCharacter` e `status.location` deve usare istanze `Types.ObjectId`.
3. **`assets.wearedEquipment` va passato in modo esplicito (`{}`).** Se manca, il sottodocumento non viene creato (verificato), e `CharactersService.findOne` / il campo GraphQL non-null `wearedEquipment: Equipment!` si rompono.

Per l'atomicità (D-03), il **pattern A con transazione** è verificato sul replica set con `connection.transaction()` di Mongoose: dentro la transazione prima la `findOneAndUpdate({ _id, currentCharacter: null })` sullo User, poi `Character.create([...], { session })`. Tre chiamate concorrenti per lo stesso utente → 1 personaggio. I perdenti vanno in WriteConflict, il driver ritenta, al secondo tentativo il filtro non trova lo User e rispondono `ALREADY_EXISTS`. Un E11000 sul nome dentro la transazione la annulla, e lo User torna a `currentCharacter: null` (verificato). Il pattern B (delete compensativo) lascia finestre e stati orfani permanenti se il processo cade tra i due passi: scartato.

Per l'unicità (D-05) si raccomanda un **indice unico con collation `{ locale: 'en', strength: 2 }` su `infos.name`**: niente backfill, protegge subito i nomi esistenti, E11000 riconoscibile da `keyPattern: { 'infos.name': 1 }`. Il nome va normalizzato prima di salvarlo (NFC, trim, spazi compressi). Un indice unico su `infos.nameKey` *senza* `partialFilterExpression` **fallisce la build** se ci sono documenti legacy senza chiave (verificato, E11000). `$toLower` di Mongo gestisce solo l'ASCII (verificato: `ÉLODIE` → `Élodie`), quindi un backfill di `nameKey` andrebbe fatto in JS.

**Primary recommendation:** creare un modulo `src/characters/creation/` senza Bull (`CharacterCreationModule`), con validator puro, tabella `race-traits.ts`, `StartingLocationService` con `RandomSource` iniettabile, `CharacterCreationService` che usa `connection.transaction()` (prima lo User, poi il Character) e mappa E11000 su `CHARACTER_NAME_TAKEN`. Poi `CharacterCreationException` (HttpException codificata), formatter GraphQL generalizzato, indice collation su `infos.name` con verifier al boot, `createAuthTestApp` esteso con un'opzione `imports`.

## Risposte puntuali alle domande di ricerca

### Q1 — Nome unico case-insensitive: collation vs `nameKey`
**Verificato (mongod 8.2.6 in locale, MongoMemoryReplSet; la CI pinna 8.0.4):**
- `schema.index({ 'infos.name': 1 }, { unique: true, collation: { locale: 'en', strength: 2 } })` funziona su un campo annidato: `Élan` blocca `élan` e `ÉLAN`, mentre `Elan` (senza accento) passa, perché strength 2 distingue i diacritici. [VERIFIED: esperimento exp1.js]
- Forma dell'errore: `MongoServerError`, `code === 11000`, `keyPattern = { 'infos.name': 1 }`. Con la collation `keyValue` è una **chiave ICU opaca** (`"313f2943…"`), non il nome: non va mai riportata nei messaggi. Con un indice `nameKey`: `keyPattern = { 'infos.nameKey': 1 }`, `keyValue = { 'infos.nameKey': 'aria' }`. [VERIFIED]
- Indice unico **non parziale** su `infos.nameKey` con documenti legacy privi del campo → `createIndex` fallisce con 11000 (i null collidono). Serve un `partialFilterExpression: { 'infos.nameKey': { $type: 'string' } }` oppure il backfill. [VERIFIED: exp3.js]
- Se la build dell'indice fallisce durante l'`autoIndex` di Mongoose, l'errore resta silenzioso a livello app: `Model.init()` rifiuta / evento `error` sul model, ma il boot prosegue. Per questo esiste già `TwitchIdIndexVerifier` (D-32 Phase 2). [VERIFIED: exp2.js + src/users/twitch-id-index.verifier.ts]
- `$toLower` di MongoDB è ASCII-only (`'ÉLODIE'` → `'Élodie'`) → un backfill server-side di `nameKey` non è corretto. Andrebbe fatto in JS con la stessa funzione di normalizzazione. [VERIFIED]

**Raccomandazione: collation index.** Niente nuovo campo persistito, niente backfill, niente evento change-stream `update` per ogni personaggio legacy (un backfill con `updateMany` farebbe ripubblicare `characterUpdated` a `CharactersService` per ogni documento). I nomi legacy sono protetti da subito.
- Nome indice esplicito, per esempio `character_name_ci_unique`. Dichiarato in `character.model.ts` dopo `SchemaFactory.createForClass`.
- **Normalizzazione del nome salvato:** `normalize('NFC')`, poi trim, poi `\s+` → `' '`. Raccomandato anche `’` → `'`, altrimenti `D'Artagnan` e `D’Artagnan` convivono (la collation li considera diversi). Questo altera il carattere mostrato: **[ASSUMED] da confermare con l'utente** (vedi Open Questions). Se l'utente vuole conservare il glifo tipografico, l'alternativa coerente è `nameKey` più indice parziale più backfill JS.
- Verifier al boot (`CharacterNameIndexVerifier`, clone di `TwitchIdIndexVerifier`): `characterModel.createIndexes()` in `onApplicationBootstrap`; su E11000 un log `error` che spiega che l'unicità dei nomi non è garantita, senza bloccare il boot.
- `locale: 'it'` e `'en'` sono equivalenti a strength 2 per l'alfabeto latino [ASSUMED]: si sceglie `'en'` e lo si documenta.

### Q2 — Atomicità "un personaggio per utente"
**Raccomandazione: pattern A (transazione)**, con questo ordine dentro la transazione:
1. `userModel.findOneAndUpdate({ _id: userId, currentCharacter: null }, { $set: { currentCharacter: characterId } }, { session, new: true })`. Se restituisce `null` → `CHARACTER_ALREADY_EXISTS`: l'eccezione annulla la transazione e non viene ritentata.
2. `characterModel.create([{ _id: characterId, ...startingState }], { session })` (la forma array è obbligatoria per passare `session`). E11000 su `infos.name` → `CHARACTER_NAME_TAKEN`, mappato **fuori** dalla callback, dopo l'abort.

`characterId = new Types.ObjectId()` è pre-generato: uno User non punta mai a un id inesistente fuori dalla transazione.

**Verificato** (exp1.js, `conn.transaction()` di Mongoose 8.18.1 su replica set): 3 chiamate concorrenti per lo stesso User (due con lo stesso nome) → `['ok attempts=1', 'err ALREADY_EXISTS attempts=2', 'err ALREADY_EXISTS attempts=2']`, 1 solo Character, `user.cur` = id del vincitore. Il driver ritenta da solo i `TransientTransactionError` (WriteConflict) e `UnknownTransactionCommitResult`. La transazione con E11000 sul nome di un secondo utente → abort, e lo User resta `cur: null`.

**Perché non il pattern B:** "crea il Character, poi update condizionato, poi delete compensativo" lascia un Character orfano che occupa il nome se il processo muore tra i passi (nome bruciato per sempre). La variante "prima lo User, poi il Character" lascia uno User che punta a un id inesistente: `me` lo popola come `null`, il FE mostra la pagina di creazione e la mutation risponde ALREADY_EXISTS in loop. La transazione elimina entrambi i casi.

**Prerequisiti:**
- Produzione: le transazioni richiedono un replica set. La produzione lo è già, perché `CharactersService.onModuleInit` apre un change stream, che esiste solo su replica set. [VERIFIED: src/characters/characters.service.ts]
- Test: la decisione Phase 1 dice "pre-create collection prima delle transazioni multi-doc". `createAuthTestApp.close()` fa `dropDatabase()`, quindi ogni file di test riparte senza collection. Nel `beforeAll` va fatto `await Promise.all([User, Character, City, PointOfInterest].map((name) => connection.model(name).init()))`: `init()` crea collection e indici. Tra un test e l'altro `clearDatabase()` fa solo `deleteMany`, quindi collection e indici sopravvivono.
- Iniezione: `@InjectConnection() private readonly connection: Connection` (da `@nestjs/mongoose`). Oggi nessun file in `src/` usa transazioni Mongo. Attenzione al nome: `CharactersService.doTransaction` è la compravendita del negozio, non una transazione DB. Chiamare il metodo `createCharacter` e il helper qualcosa come `claimAndInsert`, non `transaction`.

**Change stream:** `CharactersService` osserva solo `operationType ∈ {update, replace}` sulla collection `characters`. L'insert del nuovo Character non pubblica nulla e lo User non è osservato. L'abort di una transazione non emette eventi. Nessun effetto collaterale. Il nuovo personaggio diventa sottoscrivibile (`characterUpdated(id)`) dalla prima modifica successiva. [VERIFIED: codice]

### Q3 — Enum GraphQL come campi di input
**Verificato sul wire** (sonda nello scratchpad montata su `createAuthTestApp`):
- `@Field(() => RaceType) race: RaceType` in un `@InputType()` genera `race: RaceType!` e aggiunge `enum RaceType { … }` all'SDL. Convive senza problemi con `CharacterInfos.race: String!` in output. Oggi `src/schema.gql` **non contiene** `RaceType`, `ClassType`, `SexType`, `PronounType` (nessun campo li referenziava): lo schema rigenerato li aggiunge, in modo additivo.
- `sortSchema: true` (in `createGraphQLOptions`) ordina tipi e campi. Input atteso:

```graphql
input CreateCharacterInput {
  age: Int!
  background: String
  classType: ClassType!
  imagePath: String
  name: String!
  pronoun: PronounType!
  race: RaceType!
  sex: SexType!
}
```
- Variabili JSON `{ "race": "human" }` → accettate (il valore nel resolver è la stringa `'human'` = `RaceType.human`). Il FE invia `enum.name` via variabili: i nomi Dart coincidono uno a uno (verificato su `lib/models/enums/{race,class,sex,pronoun}_type.dart`).
- Enum sconosciuto via variabili → **HTTP 200**, `errors[0].extensions.code = "BAD_USER_INPUT"`, messaggio `Variable "$input" got invalid value "orc" at "input.race"; Value "orc" does not exist in "RaceType" enum.` Il resolver non viene chiamato, quindi nessun documento. Lo stesso vale per `age` non intero o campi obbligatori mancanti. (Apollo 4: `status400ForVariableCoercionErrors` è `false` di default.) Un letterale inline invalido darebbe invece `GRAPHQL_VALIDATION_FAILED` con HTTP 400: il FE usa variabili. [VERIFIED: wire + node_modules/@apollo/server/dist/cjs/requestPipeline.js]
- Un campo opzionale assente arriva come **chiave assente** (`input.background === undefined`), non come `null`. Il validator deve gestire `undefined | null | ''`.
- Per i campi opzionali va dichiarato il tipo esplicito: `@Field(() => String, { nullable: true }) background?: string | null`. Con `string | null` la reflect-metadata produce `Object`.

### Q4 — Errori tipizzati con `extensions.code` stabile
**Catena reale (letta in node_modules e verificata sul wire):**
1. Il resolver lancia un'eccezione. Il `ExternalExceptionFilter` di Nest **registra come ERROR** ogni `Error` che non sia `IntrinsicException`. `HttpException extends IntrinsicException`, quindi le HttpException non vengono loggate e i `GraphQLError` sì (verificato: `ERROR [ExceptionsHandler] GraphQLError: Nome già in uso` con stack).
2. graphql-js copia `originalError.extensions` nell'errore localizzato.
3. Il `wrapFormatErrorFn` di `@nestjs/apollo` (apollo-base.driver.js:144-195): per ogni HttpException sostituisce `extensions.code` (400 → `BAD_REQUEST`, 401 → `UNAUTHENTICATED`, 403 → `FORBIDDEN`, 422 → `BAD_USER_INPUT`, tutto il resto → `INTERNAL_SERVER_ERROR` + `status`) e aggiunge `originalError` (il body della response).
4. Poi gira il `formatError` utente (`formatAuthError`), che oggi ripristina solo i codici `AuthErrorCode` e ripulisce `originalError`/`stacktrace`.

Verificato: una `BadRequestException` codificata con `CHARACTER_AGE_OUT_OF_RANGE` arriva oggi come `{"code":"BAD_REQUEST","originalError":{…"code":"CHARACTER_AGE_OUT_OF_RANGE"}}`, cioè sbagliata e con dettagli interni esposti.

**Pattern da usare:**
- `src/characters/creation/character-creation-error-code.enum.ts`: valori uguali ai nomi (stesso test di `AuthErrorCode`): `CHARACTER_NAME_INVALID`, `CHARACTER_NAME_TAKEN`, `CHARACTER_AGE_OUT_OF_RANGE`, `CHARACTER_ALREADY_EXISTS`, `STARTING_LOCATION_UNAVAILABLE`, `BAD_USER_INPUT`.
- `CharacterCreationException extends BadRequestException`, costruttore privato più factory statiche (`nameInvalid()`, `nameTaken()`, `ageOutOfRange()`, `alreadyExists()`, `startingLocationUnavailable()`, `invalidInput(message)`), body `{ statusCode: 400, error: 'Bad Request', message, code }`, `this.code` e `this.extensions = { code }`, esattamente come `AuthException`. Si sceglie 400 perché se il formatter mancasse il codice fallback sarebbe `BAD_REQUEST` e non `INTERNAL_SERVER_ERROR`.
- **Formatter generalizzato:** sostituire il controllo `original instanceof AuthException` con "è una `HttpException` con `extensions.code` stringa" (type guard `isCodedHttpException`). Il fallback `readNestBodyCode` resta limitato agli `AuthErrorCode`, che serve per i 401 del guard. Boy Scout: rinominare in `formatDomainError` / `src/graphql/format-domain-error.ts`, aggiornare `createGraphQLOptions`, `graphql-options.factory.spec.ts` (`expect(options.formatError).toBe(...)`) e spostare `format-auth-error.spec.ts`, aggiungendo un caso per un codice `CHARACTER_*`. Il comportamento per gli errori auth resta identico, coperto dai test esistenti più `auth.resolver.int-spec.ts`.
- I messaggi in italiano vanno nel `message` (sono il `message` del GraphQL error). Il FE mappa solo `code`.

### Q5 — `@CurrentUser()` e la forma dello `User` restituito
- Il pattern da copiare è `AuthResolver.me`: `@CurrentUser() identity: AuthIdentity` → `identity.userId` (stringa dell'ObjectId dello User). Sia la sessione JWT sia il dev bypass producono uno `userId` reale a DB.
- Dopo il commit restituire `this.usersService.findOne(identity.userId)`: `findById(...).populate('currentCharacter')`. È un populate a **un solo livello**: `currentCharacter.status.location`, `status.spells` e `assets.*` restano ObjectId. Verificato: il populate di un ref `Mixed` funziona (restituisce il Document, `id` corretto), mentre `status.location` del personaggio popolato è un `ObjectId`.
- Il FE oggi seleziona solo `currentCharacter { id }` (`AuthQueries.getMe`, `AuthSessionFragment`, verificato in `lib/graphql/`) e carica il personaggio completo con `character(id)` (`CharactersService.findOne` popola tutto). **BACKEND-NOTES deve dire:** sul `User` restituito da `createCharacter` selezionare `currentCharacter { id }` (più eventuali campi scalari di `infos`). Non `status { location { … } }`, `spells`, `assets.*.item`, che non sono popolati e fallirebbero sui campi non-null.
- Caso limite: User cancellato con un JWT ancora valido (15 min). Il filtro `{ _id, currentCharacter: null }` non trova nulla e si risponderebbe ALREADY_EXISTS. Accettabile. Opzionale: in caso di miss distinguere con un `exists({ _id })` e lanciare `NotFoundException`.

### Q6 — Città di partenza
- `City.type` è `String` enum `CityType`; `City.markerLocation` è un ref **`Mixed`** con `required: true` verso `PointOfInterest` (verificato). Nei dati creati via Mongoose è un `ObjectId` (verificato con `lean()`).
- Query raccomandata: `cityModel.find({ type: { $in: homeTypes } }).select({ markerLocation: 1 }).sort({ _id: 1 }).lean()`. L'ordinamento stabile serve al determinismo nei test. Si scelgono solo le città con `markerLocation instanceof Types.ObjectId`. Pick **piatto** con `RandomSource` tra *tutte* le città esistenti dei tipi patria. Per umani e mezzelfi questo degrada bene: se è seedata una sola delle quattro capitali si parte da lì. `STARTING_LOCATION_UNAVAILABLE` arriva solo se l'insieme è vuoto. Un pick a due stadi (prima il tipo, poi la città) fallirebbe sul tipo estratto senza città.
- Opzionale ma consigliato: `poiModel.exists({ _id: markerLocation })`, e se manca `STARTING_LOCATION_UNAVAILABLE`. Senza il POI, `character(id)` popolerebbe `status.location` a `null`, che fallisce sul campo non-null `location: PointOfInterest!`.
- `RandomSource`: classe astratta come token DI, stesso pattern di `src/auth/clock.ts` (`abstract class Clock` + `SystemClock`). `abstract pickIndex(length: number): number`, implementazione `MathRandomSource` (`Math.floor(Math.random() * length)`; non è un uso di sicurezza). Nei test: `FixedRandomSource` in `test/characters/` più `overrideProvider(RandomSource)`. Serve quindi l'override nel test app (vedi Q9).
- **Fixture City (nuova):** `test/fixtures/city.fixture.ts`, two-tier come `poi.fixture.ts`:
  - `buildCity(overrides)` → `{ type: 'drusteaCapital', name: 'Test City', area: [], markerLocation: new Types.ObjectId(), relatedLore: null, pointsOfInterest: [], ...overrides }`
  - `persistCity(model, overrides, poiModel?)`: se `poiModel` è passato e `overrides.markerLocation` no, crea un POI reale con `persistPoi(poiModel, { city: <id città> })` e lo usa (stesso schema di `persistCharacter`).
  - Va esportata da `test/fixtures/index.ts` e coperta in `fixtures.spec.ts` / `fixtures.int-spec.ts` (convenzione Phase 1).
- `persistPoi(model, overrides)` crea `{ type: 'city', location: [0,0], city: new ObjectId(), quest: null }`. Nota della fixture: `type` è una String scalare a DB anche se il GraphQL dichiara `[PoiType]`.
- WARN al boot (D-10, a discrezione: **raccomandato**). `StartingCitiesReporter implements OnApplicationBootstrap`: un `distinct('type')` sulle città, poi per ogni razza senza alcuna città patria un `logger.warn`. Non lancia mai (try/catch con log `error`, come `TwitchIdIndexVerifier`).

### Q7 — Dove vive la validazione
- Confermato: nessun `ValidationPipe` né class-validator nel progetto (grep). La validazione è procedurale.
- Moduli **puri** (niente Nest, niente Mongoose), unit-testabili:
  - `src/characters/creation/race-traits.ts`: `RACE_TRAITS: Readonly<Record<RaceType, { minAge: number; maxAge: number }>>` e `RACE_HOME_CITY_TYPES: Readonly<Record<RaceType, readonly CityType[]>>`. `Record<RaceType, …>` rende la tabella **esaustiva a compile time**: una razza aggiunta senza riga fa fallire `tsc`/`nest build` in CI.
  - `src/characters/creation/character-name.ts`: `normalizeCharacterName(raw)` e `isValidCharacterName(normalized)`.
  - `src/characters/creation/create-character-input.validator.ts`: `validateCreateCharacterInput(input) → NormalizedCharacterInput`, che lancia `CharacterCreationException`. Ordine: nome, età, background, imagePath.
- Regex: `/^[\p{L}'’ -]+$/u`. Target `esnext` e Node 22.12 supportano gli Unicode property escapes. **Normalizzare a NFC prima del test:** `'Élodie'` (decomposto) **fallisce** `\p{L}` perché U+0301 è `\p{M}`, mentre `'Élodie'` composto passa (verificato). La compressione `\s+` → `' '` trasforma anche NBSP e simili in spazi normali. Gli zero-width joiner restano rifiutati (verificato).
- Lunghezze: per il nome contare i code point (`[...name].length`): la regex ammette solo lettere, quindi dopo NFC code point e grafemi coincidono per gli alfabeti comuni. Per il background usare i **grafemi** (`new Intl.Segmenter('it', { granularity: 'grapheme' })`). Il `maxLength` dei `TextField` Flutter conta i grafemi: con `.length` (UTF-16) il BE rifiuterebbe testi che il contatore FE accetta (verificato: famiglia emoji = 1 grafema, 5 code point, 8 unità UTF-16). Un helper unico `countGraphemes` va bene anche per il nome.
- `imagePath`: `undefined | null | ''` → `null`. Altrimenti `new URL(value)` in try/catch, `protocol === 'https:'` e lunghezza ≤ 2048, se no `BAD_USER_INPUT`. (Il mock di test di Cloudinary restituisce `https://cdn.test/image.png`, che è compatibile.)
- `background`: trim, `''` se assente, più di 500 grafemi → `BAD_USER_INPUT`.
- Età: `RACE_TRAITS[race]`, `minAge ≤ age ≤ maxAge` (gli estremi sono inclusi), altrimenti `CHARACTER_AGE_OUT_OF_RANGE`. Il tipo intero è già garantito da GraphQL `Int`.

In alternativa la cartella può essere `src/characterCreation/` (lo stile camelCase di `pendingQuests/`, `pointsOfInterest/`). È a discrezione, ma va scelta una volta sola.

### Pattern 1: flusso del service
**What:** validazione pura, poi la location (letture fuori dalla transazione), poi la transazione corta (claim dello User, insert), poi la rilettura popolata.
**When to use:** sempre per `createCharacter`.

### Pattern 2: tabella unica tipizzata per razza
`Record<RaceType, …>` più `raceTraits()` derivata con `Object.values(RaceType).map(race => ({ race, ...RACE_TRAITS[race] }))`, nell'ordine di dichiarazione dell'enum. Il test unitario confronta con la tabella D-06 riga per riga e verifica 9 voci.

### Pattern 3: eccezione di dominio codificata
Clone di `AuthException` (costruttore privato, factory statiche, `code`, `extensions`). Il test unitario copia `auth.exception.spec.ts`: valori uguali ai nomi, `getStatus() === 400`, body.

### Pattern 4: builder puro dello stato iniziale
`buildStartingCharacter(normalized, locationId: Types.ObjectId)` restituisce il documento completo D-09. Va **passato tutto in modo esplicito**: `assets.wearedEquipment: {}`, `quests.completedQuests: []`, `status.xp: 0`, `coins { gold: 0, silver: 5, copper: 0 }` e così via, senza affidarsi ai default dello schema (alcuni mancano: `level` ha default 0, `title` nessuno, `currentLifePoints` nessuno). Il test unitario confronta con l'oggetto atteso.

### Anti-Patterns to Avoid
- **Mettere la mutation in `CharactersModule`:** porta con sé Bull (`registerQueue('spell-recovery')`), quindi Redis in ogni test di creazione.
- **Pre-check `findOne({ 'infos.name': … })` come unica garanzia di unicità:** introduce una race. Il pre-check, se si fa, è solo UX: la verità è l'E11000. Con l'indice collation il pre-check dovrebbe anche usare `.collation(...)` per avere la stessa semantica, quindi meglio non farlo.
- **Lasciare uscire un E11000 o un `ValidationError` di Mongoose dal service:** diventa `INTERNAL_SERVER_ERROR` con il messaggio `E11000 duplicate key…` sul wire, più un log ERROR.
- **Passare id stringa a campi `Mixed`:** verificato, `currentCharacter` viene salvato come stringa.
- **Selezionare campi annidati non popolati sullo `User` restituito** (vedi Q5).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Unicità case-insensitive | lock applicativi / pre-check | indice unico con collation strength 2 | atomico, gestisce il case folding Unicode (ICU) |
| Retry di transazioni in conflitto | loop manuale su `TransientTransactionError` | `connection.transaction(fn)` (wrappa `withTransaction` e resetta lo stato dei documenti ai retry) | verificato: attempts=2 automatici |
| Case folding / lowercase per la chiave | `$toLower` in pipeline | collation (oppure `String.prototype.toLowerCase` JS se si sceglie `nameKey`) | `$toLower` è ASCII-only (verificato) |
| Conteggio caratteri visibili | `.length` | `Intl.Segmenter` (grafemi) | coerenza con il `maxLength` Flutter |
| Validazione enum | controlli manuali su `race`, `sex`… | enum GraphQL nell'input | rifiuto nativo `BAD_USER_INPUT` prima del resolver |
| Parsing URL | regex `^https://` | `new URL()` + `protocol` | edge case (spazi, schemi strani) |

**Key insight:** la semantica di unicità e atomicità deve stare nel database (indice e transazione). Il codice applicativo traduce solo gli esiti in codici stabili.

## Common Pitfalls

### Pitfall 1: codice di dominio riscritto in `BAD_REQUEST`
**What goes wrong:** il FE riceve `BAD_REQUEST` più `originalError` invece di `CHARACTER_*`.
**Why it happens:** `@nestjs/apollo` riscrive `extensions.code` di ogni HttpException e il formatter attuale ripristina solo gli `AuthErrorCode`.
**How to avoid:** formatter generalizzato (Q4) più un int-test che asserisce `extensions` **uguale** a `{ code }` (niente `originalError` né `stacktrace`), come fa `auth.resolver.int-spec.ts:116`.
**Warning signs:** `extensions.originalError` presente nelle risposte.

### Pitfall 2: ref `Mixed` senza cast
**What goes wrong:** `currentCharacter` o `status.location` salvati come stringa.
**How to avoid:** usare sempre `Types.ObjectId` (`characterId = new Types.ObjectId()`, `markerLocation` filtrato con `instanceof Types.ObjectId`). Nell'int-test asserire sul documento raw (`collection.findOne`) che `currentCharacter instanceof ObjectId`.

### Pitfall 3: `wearedEquipment` mancante
**What goes wrong:** con `assets: {}` il sottodocumento `wearedEquipment` non esiste (verificato). `CharactersService.findOne` fa `wearedEquipment[slot]` su `undefined` e lancia TypeError, e `wearedEquipment: Equipment!` non è risolvibile.
**How to avoid:** `wearedEquipment: {}` esplicito nel builder (Mongoose crea gli slot a `null`, verificato). Nel test di integrazione chiamare anche `character(id)` sul personaggio creato.

### Pitfall 4: indice non ancora costruito nel test di unicità
**What goes wrong:** il test "nome duplicato → NAME_TAKEN" passa o fallisce a seconda del timing, perché `autoIndex` è asincrono e il DB `auth-test` viene droppato a ogni `close()`.
**How to avoid:** nel `beforeAll` fare `await model.init()` per User, Character, City, POI. Crea anche le collection prima delle transazioni (decisione Phase 1).

### Pitfall 5: NFC
**What goes wrong:** un nome valido scritto con lettere decomposte (tipico di input macOS o copia-incolla) viene rifiutato da `\p{L}`, oppure collide a metà con un nome composto.
**How to avoid:** `normalize('NFC')` come primo passo, coperto da un test unitario (verificato: `'Élodie'` fallisce senza NFC).

### Pitfall 6: dev bypass in cache
Vedi Q9: usare `createAuthenticatedUser`.

### Pitfall 7: `npm run lint` / formattazione globale
Riscrive file non correlati. Solo `npx prettier --write <file>` e `npx eslint <file>`. I file nuovi devono essere eslint-clean, perché la CI esegue `npm run lint`.

### Pitfall 8: schema non committato
La CI fallisce su `git diff --exit-code src/schema.gql`. Lo schema va rigenerato **dopo** l'ultimo cambio a input e type e committato.

### Pitfall 9: messaggio di E11000 o chiave collation esposti
**How to avoid:** mappare con `isDuplicateKeyOn(error, 'infos.name')` (controllo di `code === 11000` e della chiave in `keyPattern`). Gli altri E11000, come quello su `_id` (teoricamente impossibile), vanno rilanciati. Il messaggio esce solo dalla factory: "Nome già in uso".

```typescript
// Source: generalizzazione di src/auth/format-auth-error.ts
function isCodedHttpException(error: unknown): error is HttpException & { extensions: { code: string } } {
    return (
        error instanceof HttpException &&
        typeof (error as { extensions?: { code?: unknown } }).extensions?.code === 'string'
    );
}

function resolveDomainErrorCode(formatted: GraphQLFormattedError, error: unknown): string | undefined {
    const original = unwrapResolverError(error);
    if (isCodedHttpException(original)) return original.extensions.code;
    if (isCodedHttpException(error)) return error.extensions.code;
    return readNestBodyAuthCode(formatted); // invariato: solo AuthErrorCode (401 del guard)
}
```

```typescript
    throw error;
}
return this.usersService.findOne(userId);
```

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Creazione per conto di un altro utente | Spoofing / Elevation | identità dal bearer soltanto (D-01, D-15) |
| Doppio submit / race → due personaggi | Tampering | transazione con claim condizionato dello User |
| Nome omografo/impersonazione (`Aria`/`ARIA`, NFD/NFC, `'`/`’`) | Spoofing | collation strength 2, NFC, normalizzazione dell'apostrofo (A1) |
| Leak interno via messaggi d'errore (E11000, stack) | Information disclosure | mappatura in factory e formatter che ripulisce |
| `imagePath` verso host arbitrario (tracking pixel, contenuti NSFW) | Information disclosure / abuse | solo https in questa fase; allowlist host e moderazione → BE-HARD (debito esplicito) |
| Enumerazione dei nomi via `CHARACTER_NAME_TAKEN` | Information disclosure | accettato: i nomi dei personaggi sono pubblici nel gioco. Rate limiting → BE-HARD |
| Payload enorme nel background | DoS | limite di 500 grafemi dopo il parse; limite del body Express di default |
