### WR-01: I limiti di lunghezza contano solo i grafemi: un nome di 2 "caratteri" o un background di 500 può pesare decine di KB

**Files modified:** `src/characters/creation/character-name.ts`, `src/characters/creation/character-name.spec.ts`, `src/characters/creation/create-character-input.validator.ts`, `src/characters/creation/create-character-input.validator.spec.ts`, `.planning/phases/02.1-character-creation-contract/BACKEND-NOTES.md`
**Commit:** `e97a479` — `fix(characters): cap character names and backgrounds in UTF-16 units too`
**Applied fix:** Kept the grapheme semantics the app relies on and added a hard UTF-16 ceiling beside each count, as suggested by the review:
- `CHARACTER_NAME_MAX_CODE_UNITS = CHARACTER_NAME_MAX_LENGTH * 2` (40) checked first in `isValidCharacterName` (no combining marks are allowed, so a legitimate letter is at most one surrogate pair).
- `BACKGROUND_MAX_CODE_UNITS = BACKGROUND_MAX_GRAPHEMES * 8` (4000) checked alongside the grapheme count in `normalizeBackground`; the existing "500 ZWJ emoji families = 4000 units" test still passes exactly at the ceiling.
- Red tests: `isValidCharacterName('ᄀ'.repeat(100) + 'a')` → `false` (2 graphemes, 101 units); background `'a' + '́'.repeat(5000)` → `BAD_USER_INPUT`. Boundary guard added: 20 Deseret letters (40 units, 20 graphemes) are still accepted.
- Handoff §3 (name rule 4, background) and precisazione 5 document both ceilings and state the FE does not need to replicate them.

### WR-02: Le lettere modificatrici (`\p{Lm}`) soddisfano la regola "almeno una lettera" di D-19 e aggirano la normalizzazione dell'apostrofo

**Files modified:** `src/characters/creation/character-name.ts`, `src/characters/creation/character-name.spec.ts`, `src/characters/creation/create-character-input.validator.spec.ts`, `src/characters/creation/character-creation.resolver.int-spec.ts`, `.planning/phases/02.1-character-creation-contract/BACKEND-NOTES.md`
**Commit:** `f00c29c` — `fix(characters): normalize modifier-letter apostrophes and require a base letter in names`
**Applied fix:** Took the review's primary (non "hard line") option, so `\p{L}` stays the allowed class and Lm letters remain usable inside a name (ʻokina, Japanese `ー`):
- `TYPOGRAPHIC_APOSTROPHE = /’/g` → `APOSTROPHE_LOOKALIKES = /[’ʼʻ]/g` (U+2019, U+02BC, U+02BB) in `normalizeCharacterName`.
- `ANY_LETTER = /\p{L}/u` → `ANY_BASE_LETTER = /[\p{Lu}\p{Ll}\p{Lt}\p{Lo}]/u` in `isValidCharacterName`.
- Red tests (8 unit + 1 wire): `normalizeCharacterName('DʼArcy')` → `"D'Arcy"`, `('Hawaiʻi')` → `"Hawai'i"`; `isValidCharacterName` rejects `'ʼʼ'`, `'ˈˌ'`, `'ـــ'`, `'ーー'` and still accepts `'スーパー'`; validator rejects `'ˈˌ'` with `CHARACTER_NAME_INVALID`; the wire test "treats a typographic apostrophe as the same name" became an `it.each(['D’Arcy', 'DʼArcy'])` — before the fix the U+02BC variant really created a second, visually identical character under the strength-2 collation.
- Handoff §3 (rules 2, 5, 6) and precisazione 4 updated.

**Files modified:** `src/characters/creation/character-creation.service.ts`, `src/characters/creation/character-creation.resolver.int-spec.ts`, `.planning/phases/02.1-character-creation-contract/BACKEND-NOTES.md`
