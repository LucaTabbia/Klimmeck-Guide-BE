## Lint, format, test

- MAI `npm run lint` (esegue `eslint --fix` su tutto il repo e riscrive file non correlati) né `npm run format`, né prettier su una directory: solo `npx prettier --write <file>` e `npx eslint <file>` sui file `.ts` toccati, uno per uno (in zsh una variabile con più percorsi NON si spezza). Un file da modificare che fallisce GIÀ `npx prettier --check <file>` riceve PRIMA un commit separato `style(<scope>): format <file>` (solo Prettier), poi la modifica.
- Jest: `npx jest <percorsi> --selectProjects unit` / `npx jest <percorsi> --selectProjects integration --runInBand`, con i percorsi PRIMA di `--selectProjects`; integration sempre `--runInBand`; MAI jest in background; a fine di OGNI task `pgrep -fl 'bin/jest'` non stampa nulla (`pgrep` vuoto esce 1: non concatenarlo con `&&`). Per task si esegue solo la spec mirata; la suite completa gira solo nel piano di gate (senza coverage se `test:cov` supera i 600 s del tool: coverage per cartella come ripiego, scritto nel piano di gate). **Trappola 15-03:** una int-spec il cui harness «bare» fallisce al `compile()` DOPO l'apertura di Mongoose lascia jest appeso per sempre (0 % CPU): se una spec non termina entro 3 minuti, `kill -TERM` del processo, poi `--detectOpenHandles --forceExit` SOLO per leggere l'esito; il fix è nel provider (`inject` con `optional: true` e default), mai `--forceExit` nel comando del piano.
- Type check: `npx tsc --noEmit -p tsconfig.json` esce 0 a fine di ogni task di codice. **Mai `npm run build` né `nest build` in questa fase** (`nest-cli.json` ha `deleteOutDir: true` e il processo BE dell'utente gira da `dist/` di questo stesso albero, porta 3001): la build vera la lancia l'orchestratore al boot reale (runbook del handoff).
- Integrazione: `MongoMemoryReplSet` condiviso (`test/setup/global-setup.ts`, URI in `process.env.MONGO_TEST_URI` solo nei test); harness GraphQL `createAuthTestApp` / `createCharactersTestApp` + `createPlayer` + `graphqlRequest`; builder `buildX/persistX` di `test/fixtures`. Nessun `jest.mock(` di moduli: override di provider (`ChanceSource` → `SeededChanceSource`, `Clock` → `FixedClock`). Nessuna rete nei test. Prove di assenza con `toEqual` sull'intero output o `Object.keys(...).sort()`, mai con un grep sul letterale. **Nessun `Math.random` nel codice della fase**: il caso del tiro dello studio arriva solo dalla porta `ChanceSource`; il tempo solo da `Clock`.

## Segreti e database reale

- MAI leggere né stampare `.env`, `.env.*` o variabili d'ambiente (niente `cat .env`, `grep … .env`, `printenv`, `env`, `set`, `echo $MONGO_URI`, `node -e` su `process.env`). Si legge solo `.env.example`.
- **Il database reale non si tocca dagli esecutori.** Nessun esecutore avvia il BE contro il database reale (`node dist/main.js`, `npm run start*`, `node --env-file=.env …` sono VIETATI). Il backfill one-off dei personaggi esistenti (CONTEXT D-11) è codice della fase con le sue spec (dry-run/apply/verify idempotente), ma lo ESEGUE solo l'orchestratore al boot reale, e un piano successivo lo rimuove in TDD prima della merge (PR in draft finché non è girato e rimosso). ## Schema GraphQL e contratto FE

- `src/schema.gql` cambia solo dal boot reale (`npx jest test/app.int-spec.ts --selectProjects integration --runInBand`) e si committa insieme al codice che lo cambia. Le modifiche SDL della fase sono **solo additive**: `git diff origin/develop -- src/schema.gql | grep -E '^-[^-]'` non stampa nulla fino alla fine della fase; dopo ogni commit `git diff --exit-code src/schema.gql` esce 0.
- Nomi del contratto FE, stabili e non negoziabili dai piani (fissati dall'orchestratore il 2026-11-07, usati dai piani FE su mock):
  - `CharacterStatus.unlockedLore: [ID!]!` — `@Prop` `[ObjectId]` ref `Lore`, default `[]`, `@Field(() => [ID])` (soli id, nessun populate), additivo e idempotente (solo add-to-set); presente su ogni lettura del personaggio e su `characterUpdated`;
  - `Character.status.knownEnemies` — `@Prop` `[ObjectId]` ref `Enemy`, default `[]`, **senza `@Field`** (interno; `type CharacterStatus` dello SDL guadagna la sola riga `unlockedLore: [ID!]!`);
  - `QuestEnemy.known: Boolean!` — field resolver per viewer su ogni voce di `Quest.infos.enemies[]` e `QuestResult.enemies[]`: `true` se l'id del nemico è in `status.knownEnemies` del personaggio corrente del bearer (`users.currentCharacter`), `true` per l'innkeeper, `false` senza personaggio; una sola lettura del personaggio del viewer per richiesta;
  - `QuestResult.loreUnlocked: [Lore!]!` — `@Prop` `[ObjectId]` ref `Lore`, default `[]`, popolato sul filo; contiene SOLO le lore aggiunte da quell'esito (differenza rispetto allo snapshot preso in sessione), mai filtrato per viewer;
  - `City.relatedLore: Lore` (già nullable) → `null` per il giocatore finché la lore della città non è in `unlockedLore`; `Lore.relatedLore` ed `Enemy.relatedLore` filtrate sull'insieme; `lores` e `lore(id)` filtrate, `lore(id)` chiusa → `ResourceNotFoundException.lore()` (stesso `NOT_FOUND` di una lore inesistente); `Quest.infos.relatedLore` NON filtrata; l'innkeeper vede tutto senza filtro; utente senza personaggio corrente → `[]` / `null` / `NOT_FOUND`;
  - `Lore.type` resta `String!`; nessuna query, mutation o subscription nuova (`EXPECTED_OWNER_ONLY_HANDLERS` invariato); `lores`/`lore`/`cities`/`city`/`enemy`/`enemys` restano le stesse operazioni.
- Regole di gioco che vincolano ogni piano (CONTEXT D-03..D-11): geografia di una città = lore della città + le sue `relatedLore` di tipo `region` e `state` (funzione pura unica), scritta alla creazione (città natale) e a ogni arrivo su un POI che è `City.markerLocation` (completamento viaggio `free`/`quest` compresa la deviazione d'imboscata, salto dell'accettazione, teleport), nella stessa transazione del movimento, idempotente, POI del territorio ignorati, marker senza città → nessuno sblocco e movimento intatto; esito `success` con nemici → `Enemy.relatedLore` di tutti i nemici del contesto in `unlockedLore` e id dei nemici in `knownEnemies` per ogni partecipante vincente (individuale, party, dungeon, imboscata vinta), nello stesso update del piano; sconfitta/soccorso/morte/`gmCompleted` senza combattimento → nulla; `study` vinta senza `spellLearned` → con probabilità `LORE_STUDY_CHANCE` una lore casuale fra le non sbloccate dei `STUDY_LORE_TYPES`, pool letto nel loader ordinato per id e tirato con `ChanceSource`, pool vuoto → nulla; `loreUnlocked` = sole novità dell'esito; nessuna cascata sulle `relatedLore`.
- Nomi interni fissati per i piani (il planner può aggiungerne, non rinominare questi): `src/lore/lore-geography.ts` (`geographyOf`), `src/lore/lore-visibility.ts` (filtro per insieme), `src/lore/known-enemies.resolver.ts` (field resolver `known` con cache per request), `src/lore/study-lore-types.ts` (`STUDY_LORE_TYPES`), `src/config/lore-config.ts` (`LORE_CONFIG`, `LORE_STUDY_CHANCE`), `src/characters/lore/` o `src/characters/creation/` per la geografia alla nascita, `src/migrations/lore-backfill/` per il one-off (CLI `--dry-run/--apply/--verify` come il piano 10-26, rimosso prima della merge); campi `status.unlockedLore` e `status.knownEnemies` in `character-status.model.ts`; `loreUnlocked` in `quest-result.model.ts` accanto a `spellLearned`.
