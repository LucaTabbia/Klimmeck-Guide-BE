# Phase 09.2: Code Review Report

## Summary

The phase is sound. No critical issue, no transaction or ownership defect found. `npx tsc -p tsconfig.build.json --noEmit` and `npx eslint` on the touched production files are clean; no jest process left running.

What was checked and found correct:

- **Transactions.** Every write of the archive (user link check, character `deletedAt`, seat release, placeholder marker, quest reset) and of the death unlink on confirmation uses the caller's `session`. The confirmation runs in `connection.transaction`, so a write conflict between two concurrent confirmations or against `deleteCharacter` is retried and the loser sees `null` and answers the idempotent success. The `findOneAndUpdate` projection returns the pre-update document, which is all the confirmation needs (`outcome`, `character`).
- **Race death vs `deleteCharacter`.** Both write the same character document, so one of them is retried: either the death sees the user unlinked and records nothing, or `deleteCharacter` finds the character already archived and falls into the "unlinked anyway" branch. The user is never left stuck.
- **Ownership.** The mutation is guarded by `@OwnsQuestResult` (malformed id gives NOT_FOUND without a DB read, foreign result or innkeeper gives FORBIDDEN, no audit); the list filters on the bearer user only; an unreadable `userId` yields `[]` or NOT_FOUND, never another user's data. The `user` condition kept in the update filter is a correct second line of defence.
- **Placeholder logic.** `unstartedSeatReleaseOf` and `placeholderMarkOf` are disjoint on the `startedAt` condition; both id forms are covered by `idForms` (including the `arrayFilters` entry); the active-registrant check runs after the character's own archive write in the same session, so the character being archived is already excluded. The marker is a real write on the quest document, which serialises concurrent archives and makes the change stream emit.
- **`currentCharacter` readers.** The populate filter `CURRENT_CHARACTER_LINK_FILTER` only admits active or death-archived characters. All gameplay paths read the character with the active filter (`activeCharacterById` / `ACTIVE_CHARACTER_FILTER`: acceptance, wallet, trade, equipment, spells, travel, abandon, pending requests, roster loaders), so a dead-but-current character cannot act. `ownersOf` and `notifyOwner` now resolve a dead-but-current owner, but their callers only pass ids that come from active-filtered reads, so no push or result reaches a dead character.
- **Boot maintenance.** Index build and backfill are wrapped separately, failures are logged with name and code only (`describeError`), the boot is never aborted.
- **Schema.** `src/schema.gql` diff is exactly three additive lines; the internal marker has no `@Field` and is covered by the real-boot `not.toMatch`.

One contract mismatch between `BACKEND-NOTES.md` and the code is reported below, plus four minor items.

## Warnings

### WR-01: The handoff promises NOT_FOUND for a new `questResultReceived` subscribe on a dead-but-current character; the code accepts it

**File:** `src/authz/ownership/character-access.policy.ts:99-117` (owner branch of `authorizeCharacter`), `src/quests/results/quest-results.resolver.ts:60-77`; docs: `.planning/phases/09.2-quest-result-delivery-contract/BACKEND-NOTES.md:172`, `:183` and the last row of the section 4 table
**Issue:** `authorizeCharacter` returns `ResourceAccess.owner` as soon as `User.currentCharacter` equals the requested id, without checking that the character is active (the existence check runs only in the rejection branch). Before D-12 a dead character was unlinked, so the owner fell into that branch and got NOT_FOUND. Now the owner of a dead-but-current character passes the guard, and `questResultReceived` has no snapshot step that could throw, so the subscription opens normally. `characterUpdated` is fine (its snapshot reads with the active filter and throws NOT_FOUND). The handoff states, in three places, that `questResultReceived` on the dead character answers NOT_FOUND "Personaggio non trovato". The FE is told it can rely on that; the behaviour is in fact the opposite and no spec covers it (the only dead-character spec in `quest-result-received.subscription.int-spec.ts` is the "unlinked" case at line 228).

The actual behaviour is harmless (the owner only receives own results) and arguably useful, so the cheaper fix is the documentation.
**Fix:** Either correct the three places in `BACKEND-NOTES.md` ("`questResultReceived` on a dead-but-current character is accepted; it answers NOT_FOUND only after the confirmation unlinks it") and add an int-spec for it, or make the contract true by checking existence in the owner branch for subscriptions:

```ts
// character-access.policy.ts, owner branch
if ((await this.readCurrentCharacterId(identity.userId)) === characterId) {
    if (options.ownerOnly) await this.assertCharacterExists(characterId);
    return ResourceAccess.owner;
}
```

(the second option also changes `acceptQuest`, `abandonQuest` and `startTravel`, which are `ownerOnly` and already answer NOT_FOUND from their services, so it is consistent but touches more paths; prefer the documentation fix.)

## Info

### IN-01: A repeated confirmation of a `death` result never repairs the character link

**File:** `src/quests/results/quest-result-acknowledgement.service.ts:36-50`
**Issue:** The unlink runs only when the conditional update actually matched. Normally the two writes are atomic, so the link and the confirmation cannot diverge. They can diverge only through out-of-band operations: the mongosh command in handoff section 7 ("confirm every pending result") run without the second command, or the boot backfill touching a death result of a user who is still linked. In that state the FE retry is a no-op and the user stays bound to the dead character, with `createCharacter` refused; the only way out is `deleteCharacter`. D-12 declares no safety net, so this is not a defect, but the repair is one cheap, already-conditional write.
**Fix:** Optionally, when the update matched nothing, look the result up (`outcome`, `character`) and, if it is a `death`, run the same conditional `deathUnlinkOf` update in the session. At minimum, state in section 7 that the two mongosh commands must be run together.

### IN-02: The boot awaits the index build and a full-collection scan on every start

**File:** `src/quests/results/quest-result-maintenance.ts:24-40` and `src/quests/results/quest-result-acknowledgement.ts:41-43`
**Issue:** `onApplicationBootstrap` awaits `createIndexes()` and then an update over the filter on the missing field. Errors are handled, but duration is not: on a large collection the application does not accept traffic until the index is built and the unindexed scan completes, on every restart (the handoff already notes the scan for Phase 10). Also, the schema index is already created by Mongoose at connection time, so `createIndexes()` mostly duplicates it. Acceptable at today's volumes.
**Fix:** When volumes grow, run the maintenance without awaiting it (log on rejection) or remove the backfill after the first deploy, as already planned for Phase 10.

### IN-03: `new Date()` feeds the placeholder marker and the archive timestamp

**File:** `src/characters/deletion/character-deletion.service.ts:51` (pre-existing line, outside the diff)
**Issue:** `archiveCurrentCharacter` passes `now: new Date()` to the archiver, which now persists it into the quest registration marker as well as into the character deletion timestamp. The project rule is to use `Clock`; the new code of the phase respects it (`this.clock.now()` in the confirmation), but this call site makes the marker untestable with a fixed clock on the `deleteCharacter` path (the specs reach the archiver directly with a fixed `now`).
**Fix:** Inject `Clock` in `CharacterDeletionService` and pass `now: this.clock.now()` (Boy Scout, same commit if the file is touched).

### IN-04: The "unlinked anyway" WARN is now the documented exit route, with a misleading message

**File:** `src/characters/deletion/character-archiver.ts:117-121`
**Issue:** `deleteCharacter` on a user still linked to a dead character lands in `unlinkedAnyway`, which logs a WARN saying the user "pointed to a missing or archived character". Since D-12 this is the supported way out for a user with an unconfirmed death, not an anomaly, so operators will see WARN noise that looks like data corruption.
**Fix:** Distinguish the archived-by-death case (log at `log` level, "unlinked from a dead character without confirmation") from the genuinely missing reference (keep WARN), or lower the level for both.

### IN-05: Double cast on the backfill pipeline

**File:** `src/quests/results/quest-result-maintenance.ts:54`
**Issue:** `legacyResultsBackfill() as unknown as UpdateWithAggregationPipeline` silences the type checker; the builder returns an untyped array.
**Fix:** Type the builder's return value (`UpdateWithAggregationPipeline` from mongoose, with the stage declared as a pipeline stage) and drop the cast.
