### Perché `npm test` è flaky (gap #1)
- Jest `projects` [unit, integration] in package.json:77-128. Il progetto `integration` ha
  globalSetup/globalTeardown/setupFilesAfterEnv; il progetto `unit` no.
- `test/setup/global-setup.ts` avvia UN solo `MongoMemoryReplSet` e ne espone l'URI in
  `process.env.MONGO_TEST_URI` (nessun dbName → tutti puntano al DB di default).
- `test/setup/after-env.ts` registra un `afterEach` che fa `deleteMany({})` su TUTTE le
  collection della connessione condivisa.
- `"test": "jest"` esegue unit+integration col parallelismo di default di Jest (nessun
  --runInBand): due file `*.int-spec.ts` in worker paralleli colpiscono lo STESSO database
  fisico → l'afterEach di un file cancella a metà esecuzione i documenti che un altro file
  sta ancora asserendo → `TypeError: Cannot read properties of null` / assert falliti.
  Nota: `spell-recovery.processor.int-spec.ts` usa una connessione Nest separata
  (`MongooseModule.forRoot(MONGO_TEST_URI)`), ma punta comunque allo STESSO db fisico, quindi
  è vittima della stessa cancellazione incrociata.
- `test:int` è verde perché `--runInBand` esegue i file in-band (mai due int-spec insieme).
