**Applied fix:** TDD. First added the wire test "resolves me.currentCharacter to null for a user still pointing at an archived character" to the visibility suite (`archiveDocument(alice)` with no unlink, then `{ me { currentCharacter { id } } }` with Alice's bearer). It failed as expected: `currentCharacter` came back as `{ id: <archived id> }` instead of `null`. Then `UsersService` got a module-level `CURRENT_CHARACTER_POPULATE = { path: 'currentCharacter', match: ACTIVE_CHARACTER_FILTER } as const` (it reuses the shared filter and does not repeat the literal), and both `findAll()` and `findOne()` use it. That covers `users`, `user(id)`, `me` (through `findOne`), the `userUpdated` snapshot and the publisher's re-read. There is no `users.service.spec.ts`, so no unit populate expectations needed updating. BACKEND-NOTES §Riferimento pendente now says that in this corrupt state the read paths show `currentCharacter: null` while `createCharacter` still answers `CHARACTER_ALREADY_EXISTS`, and that `deleteCharacter` unlinks the reference and realigns the state.
