## Summary

Reviewed the 30 files of `feat/03.1-character-deletion-contract` against `origin/develop` (`a562068`), with `git diff -w` on `characters.service.ts` and `spell-recovery.processor.ts` to separate the formatting commit `92c7c24` from behavior. The contract matches `03.1-CONTEXT.md` D-01..D-16: `deleteCharacter: User!` with no arguments, identity from `@CurrentUser()`, soft delete via `@Prop`-only `deletedAt`/`deletionReason`, one `connection.transaction` with the inverse claim, stable `CHARACTER_NOT_FOUND`, the shared `ACTIVE_CHARACTER_FILTER`, the partial unique index with legacy drop, archived ids answering `NOT_FOUND` on every player path for every role, change-stream `$match` on `fullDocument.deletedAt: null`, and the processor skipping archived characters.

Focus areas checked and found sound:

- **Transaction and retry.** `findOneAndUpdate({ _id, currentCharacter: { $ne: null } }, …, { returnDocument: 'before' })` followed by `updateOne(activeCharacterById(prev), …)` inside `connection.transaction`; the driver's `withTransaction` retries `WriteConflict`, the loser sees `currentCharacter: null` and gets `CHARACTER_NOT_FOUND`; `rejectUnlinked` distinguishes a deleted user (`UNAUTHENTICATED`) with a read in the same session. Nothing is written on the rejection path. Covered on the wire with three concurrent calls.
- **Dangling-reference branch.** The archive filter is `{ _id: prev, deletedAt: null }`, so the wrong document can never be archived and an already-archived one is never touched; the unlink is committed on purpose so the user is not stuck. The warning logs only the user id.
- **Change-stream race.** `updateLookup` runs before the `$match`, so an update that lands on a document archived in the meantime is filtered server-side; the handler re-reads with the active filter and swallows `ResourceNotFoundException` for the residual window. `publish()` is not awaited.
- **Verifier.** Builds the partial index first, drops the legacy index only on success, tolerates `IndexNotFound` (27) silently, logs name + code for everything else (85/86 included) and never throws; no character name reaches the logs (the duplicate-names message is static).
- **Read paths.** No `findById` remains on the `Character` model in `src/` (multi-line search included); every service, policy and processor read goes through `activeCharacterById`/`ACTIVE_CHARACTER_FILTER`.
- **Schema.** `src/schema.gql` contains `deleteCharacter: User!` and none of `deletedAt`, `deletionReason`, `DeletionReason`; the real-boot test guards it.

One warning remains: the invariant "an archived character is invisible on every player path" is not enforced on `User.currentCharacter`, which is populated without the active filter (`me`, `user`, `users`, `userUpdated`). The state is unreachable through this phase's code paths, but it is exactly the state the visibility suite constructs and the one a future archive-without-unlink would create. The remaining findings are hardening and test-hygiene notes.

## Warnings

### WR-01: `User.currentCharacter` is populated without the active filter, so an archived character can still surface through `me`/`userUpdated`

**File:** `src/users/users.service.ts:28` and `src/users/users.service.ts:33-36` (consumed by `src/users/user-updates.publisher.ts:58` and `src/users/users.resolver.ts:30,47`); the state is built but not covered by `src/characters/archived-character-visibility.int-spec.ts:242-255`
**Issue:** D-06 makes archived characters fail-closed on every player path, and every `Character` read in this phase applies `activeCharacterById`. The `User` reads do not: `findAll()` and `findOne()` call `.populate('currentCharacter')` with no `match`, so whenever a `User` still points at an archived document the full archived `Character` is returned by `me`, `user(id)`, `users` and every `userUpdated` event (the publisher re-reads through `usersService.findOne`). `deleteCharacter` itself cannot produce that state (unlink and archive are in one transaction), but the visibility suite deliberately constructs it ("a user still pointing at an archived character") and only asserts the character paths; Phase 9 or any manual archive that skips `archiveCurrentCharacter` would hit it in production. The file is outside this phase's diff, which is why the gap went unnoticed.
**Fix:** Apply the shared filter as a populate `match`, so an archived reference resolves to `null` exactly like a dangling one, and add the missing wire assertion.

```ts
// src/users/users.service.ts
import { ACTIVE_CHARACTER_FILTER } from 'src/models/character/active-character.filter';

const CURRENT_CHARACTER_POPULATE = {
    path: 'currentCharacter',
    match: ACTIVE_CHARACTER_FILTER,
} as const;

async findAll(): Promise<User[]> {
    return this.userModel.find().populate(CURRENT_CHARACTER_POPULATE).exec();
}

async findOne(id: string): Promise<User> {
    if (!isObjectIdHex(id)) throw ResourceNotFoundException.user();
    const user = await this.userModel
        .findById(id)
        .populate(CURRENT_CHARACTER_POPULATE)
        .exec();
    if (!user) throw ResourceNotFoundException.user();
    return user;
}
```

Add to `archived-character-visibility.int-spec.ts`: after `archiveDocument(alice)` (no unlink), `me { currentCharacter { id } }` with Alice's bearer must return `currentCharacter: null`. Note the trade-off for that corrupt state: the FE will see no character while `createCharacter` still answers `CHARACTER_ALREADY_EXISTS`; `deleteCharacter` already unlinks it (dangling branch), so document "call `deleteCharacter` to realign" in `BACKEND-NOTES.md` §Riferimento pendente.

## Info

### IN-01: Read-then-`save()` can still write to a document archived in between

**File:** `src/characters/spell-recovery.processor.ts:35-57`; `src/characters/characters.service.ts:183-249`, `257-264`, `272-312`, `320-336`, `344-372`
**Issue:** The active check happens at read time; `document.save()` then issues an update keyed on `_id` only. If `deleteCharacter` commits between the read and the save, the archived document is modified after `deletedAt` was set, which weakens D-04 ("no other field is altered") and the archive-as-audit intent of D-12. There is no user-visible effect (the change stream filters the archived document and every read path hides it), so this is a hardening note, not a bug.
**Fix:** For the processor, replace the read-modify-save with one atomic positional update guarded by the active filter:

```ts
const result = await this.characterModel
    .updateOne(
        {
            ...activeCharacterById(characterId),
            'assets.activeSpells.spell': new Types.ObjectId(spellId),
        },
        { $inc: { 'assets.activeSpells.$.usages': 1 } },
    )
    .exec();
if (result.matchedCount === 0) {
    this.logger.warn(`Character ${characterId} archived or spell ${spellId} not active, skipping recovery`);
    return;
}
```

For the service mutations, the smallest global guard is `CharacterSchema.set('optimisticConcurrency', true)` plus `$inc: { __v: 1 }` in the archive `$set` of `archiveCurrentCharacter`, so a stale `save()` fails with `VersionError` instead of writing. Worth a follow-up rather than this phase.

### IN-02: `new Types.ObjectId(userId)` turns a malformed identity into a 500

**File:** `src/characters/deletion/character-deletion.service.ts:33` (same pattern as `src/characters/creation/character-creation.service.ts:41`)
**Issue:** `identity.userId` comes from a verified JWT, so in practice it is always a 24-hex string; still, a malformed value throws `BSONError` and surfaces as `INTERNAL_SERVER_ERROR` instead of a typed code. `UsersService.findOne` already guards with `isObjectIdHex`.
**Fix:**

```ts
async deleteCharacter(userId: string): Promise<User> {
    if (!isObjectIdHex(userId)) throw AuthException.unauthenticated();
    await this.archiveCurrentCharacter(new Types.ObjectId(userId), DeletionReason.user_request);
    return this.usersService.findOne(userId);
}
```

### IN-03: The archive race in the change-stream handler is swallowed without any trace

**File:** `src/characters/characters.service.ts:73-77`
**Issue:** `if (err instanceof ResourceNotFoundException) return;` is the right outcome (no event, not an error), but it leaves no trace at all; when diagnosing a missing `characterUpdated` in production there is no way to tell "filtered by design" from "never emitted".
**Fix:** `this.logger.debug(\`Character ${String(id)} archived before re-read, no characterUpdated emitted\`)` before the `return` (id only, no name), and hoist `id` out of the `if` so it is in scope.

### IN-04: The dangling-reference warning cannot distinguish a missing document from an already-archived one

**File:** `src/characters/deletion/character-deletion.service.ts:68-73`
**Issue:** `matchedCount === 0` covers two different states, "the user pointed at a character that does not exist" (data corruption) and "the user pointed at a character archived earlier" (e.g. a future Phase 9 double-archive). One message for both hides which one happened.
**Fix:** One extra read in the session, ids only:

```ts
if (archived.matchedCount === 0) {
    const stale = await this.characterModel
        .exists({ _id: unlinked.currentCharacter })
        .session(session);
    this.logger.warn(
        `User ${String(userId)} pointed to ${stale ? 'an already archived' : 'a missing'} character ${String(unlinked.currentCharacter)}: unlinked anyway`,
    );
}
```

### IN-05: Negative real-time assertions are bounded by a fixed 500 ms window

**File:** `src/characters/archived-character.realtime.int-spec.ts:28`, `193-194`, `214-216`
**Issue:** `expectSilence(..., 500)` and `withTimeout(live.next(), 500)` pass vacuously if a stray event lands after 500 ms on a slow CI runner. The suites mitigate this correctly with the sentinel-first pattern (Bruno's later event is awaited before asserting Alice's silence, and change-stream events are ordered), so the risk is low; the window is a secondary guard only.
**Fix:** Keep the sentinel ordering and, for the archive event itself, add an in-process assertion through `pubSub.subscribe('characterUpdated')` (as the second test already does) so the proof does not depend on the WS timing at all; consider lifting `SILENCE_MS` to 1000 ms since the sentinel already bounds the wait.
