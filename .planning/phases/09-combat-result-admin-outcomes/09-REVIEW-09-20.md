## Summary

Il piano 09-20 introduce due cose: `aidSlotsOf` (la aid copia gli slot della quest fallita) e la subscription `questUpdated(questId: String!): Quest!` alimentata da `QuestsPublisher`, un change stream su `quests` che rilegge la quest popolata a ogni `update`/`replace`.

**Verificato e in ordine:**

- **(a) Snapshot vs primo evento.** `subscribeWithSnapshot` chiama `iterator.next()` prima di `loadSnapshot()`. `Repeater.prototype.next` esegue l'executor in modo sincrono al primo `next()` (`@repeaterjs/repeater`, `execute(r)` in `next`), e l'executor di `filter` chiama `source.next()` prima del suo primo `await`: il listener sul topic `questUpdated` è agganciato prima della `findOne` dello snapshot, anche attraverso `pipe(..., filter(...))`. La garanzia D-03 vale per `questUpdated` come per `characterUpdated` e `userUpdated`. Due subscriber ricevono ciascuno una copia dello stesso evento (listener distinti sull'`EventTarget`); nessuna duplicazione sullo stesso socket.
- **(b) Sicurezza.** `AuthGuard` è deny-by-default (`APP_GUARD`, `src/auth/auth.module.ts:55`) e sul WS prende l'identità da `extra.identity` risolta alla `connection_init`, con `assertActiveWsIdentity` che rifiuta i token scaduti; `questUpdated` non ha `@Public` quindi è autenticata. Sul filo esce lo stesso tipo `Quest` della board: `rescue`, `concludedAt`, `startedAt` non hanno `@Field`; `registeredAdventurers { character title registeredAt }` è già esposto da `quests`. L'id del client passa da `objectIdFromHex` in `findOne` (snapshot) e il filtro per evento confronta stringhe canoniche; una quest conclusa risponde `NOT_FOUND` alla subscribe e il publisher non la ripubblica (fail-closed anche se la conclusione avviene fra l'evento e la rilettura). I log portano soli id. Nessun secret, nessun eval, nessun dato altrui oltre la board.
- **(d) Chiusura.** `onModuleDestroy` chiude lo stream; `close()` su uno stream già invalidato è idempotente. In `harness.close()` il `dropDatabase()` precede `app.close()`: l'`invalidate` è filtrato dalla pipeline (`$match` su `update`/`replace`), quindi nessun `change` spurio; al più un `error` loggato con il solo nome. Stesso ciclo di vita degli altri tre publisher, gate verde.
- **(g) Aid.** `slotsOf` costruisce già oggetti nuovi tramite `rankSlotOf`, e `aidSlotsOf` li copia di nuovo: nessun riferimento condiviso con `original.requirements.requiredAdventurers` (doppia copia innocua). La fixture `RANKED_SEATS` (`rookie` x2 + jolly) è coerente con i personaggi `rookie` della int-spec del boss e l'assert `toEqual` è strutturale.

**Da sistemare:** l'ordine di pubblicazione su update ravvicinati della stessa quest non è garantito (WR-01); un caso della int-spec usa la finestra di silenzio come attesa dell'evento (WR-02). Il gate «publish solo con subscriber» è praticabile senza lazy start del change stream (IN-01).

## Warnings

### WR-01: `publishUpdated` concorrente e non serializzata per quest: su update ravvicinati l'ultimo evento pubblicato può essere il più vecchio

**File:** `src/quests/quests.publisher.ts:37-41`, `src/quests/quests.publisher.ts:54-58`
**Issue:** ogni `change` lancia `void this.publishUpdated(id)` senza coordinamento. Due update sulla stessa quest a pochi millisecondi di distanza (casi reali nel codice: `register` + `commitStart` quando l'ultima accettazione completa il party, `quest-acceptance.service.ts:318` e `quest-start.service.ts:235`; accettazione seguita da `abandonQuest`, `party-abandon.service.ts:56/66`; `releaseMembers` + `$set registeredAdventurers: []` nel timeout, `party-timeout.service.ts:148`) producono due `findOne` popolate in parallelo (7 path di populate, più round trip ciascuna). Se la prima lettura legge lo stato intermedio e completa il populate dopo la seconda, il PubSub emette prima lo stato nuovo e poi quello vecchio: il FE, che sostituisce lo stato a ogni evento, resta con un contatore k/N stale fino all'update successivo. Non c'è versione né ordinamento nel payload, quindi il subscriber non può accorgersene. In più nessuna coalescenza: una raffica di N update costa N letture popolate. La stessa race latente esiste in `UserUpdatesPublisher` (fuori diff).
**Fix:** single-flight per quest con rerun, come `PendingRequestsPublisher.requestRefresh` (`dirty` + `draining`) ma con chiave `questId`: al più una lettura in corso e una in coda per quest, e l'ultimo publish riflette sempre lo stato più recente.

```ts
private readonly inFlight = new Map<string, Promise<void>>();
private readonly dirty = new Set<string>();

onModuleInit(): void {
    this.changeStream = this.questModel.watch(QUEST_UPDATES_PIPELINE);
    this.changeStream.on('change', (change: { documentKey?: unknown }) =>
        this.requestPublish(documentIdOf(change.documentKey)),
    );
    // ...
}

// single-flight per quest con rerun (come PendingRequestsPublisher): una raffica sulla stessa quest
// costa al più una lettura in corso e una in coda, e l'ultimo evento è sempre lo stato più recente
private requestPublish(questId: string | undefined): void {
    if (!questId) return;
    this.dirty.add(questId);
    if (!this.inFlight.has(questId)) {
        this.inFlight.set(questId, this.drain(questId));
    }
}

private async drain(questId: string): Promise<void> {
    try {
        while (this.dirty.delete(questId)) {
            await this.publishUpdated(questId);
        }
    } finally {
        this.inFlight.delete(questId);
    }
}
```

Test da aggiungere alla int-spec (TDD): due `updateOne` consecutivi senza `await` intermedio sul PubSub (`$push` di bruno poi `$pull`), e l'ultimo evento ricevuto deve avere `registeredAdventurers` = `[alice]`.

### WR-02: nel caso «quest conclusa» la finestra di silenzio fa anche da attesa del change stream: assert su `debug` dipendente dal timing

**File:** `src/quests/quest-updated.subscription.int-spec.ts:273-295`
**Issue:** dopo `$set concludedAt` il test chiama `expectSilence(subscription)` (500 ms) e solo dopo verifica `expect(debug).toHaveBeenCalledWith(...)`. Se il change stream consegna l'evento oltre i 500 ms (macchina carica: il SUMMARY riporta la suite unit a 914 s in quelle condizioni) il `debug` non è ancora avvenuto e il test fallisce. È esattamente il pattern che il commento di `expectSilence` vieta («usare SOLO dopo un evento sentinella già ricevuto altrove, Pitfall 12»): qui la sentinella è il log di debug, ma viene controllata dopo la finestra invece che prima. Il caso «stays silent on updates of another quest» fa la cosa giusta (attende il publish interno, poi il silenzio); questo no.
**Fix:** attendere la sentinella (il `debug` con l'id) con `withTimeout` prima della finestra di silenzio.

### IN-01: una `findOne` popolata per ogni update di qualunque quest, anche senza subscriber: gate praticabile con un `EventTarget` che conta i listener; lazy start del change stream sconsigliato

**File:** `src/quests/quests.publisher.ts:54-58`, `src/pubsub.module.ts:24`, `src/quests/quests.resolver.ts:34-45`
**Issue:** ogni `update`/`replace` su `quests` (accettazioni, abbandoni, avvii, timeout, `backfillRegisteredAt` con `updateMany` in `party-timeout.service.ts:160`, `updateQuest` dell'esito, modifiche del catalogo) scatena `findOne` con 7 populate e, in caso di conclusione (`$set concludedAt`), una lettura garantita a vuoto. T-09-98 lo accetta come «low», ma il gate è a basso costo e non tocca lo schema. `createPubSub` accetta `{ eventTarget }` (`node_modules/@graphql-yoga/subscription/cjs/create-pub-sub.js`): un `EventTarget` che tiene traccia dei listener per topic risponde «ci sono subscriber per `questUpdated:<id>`?». Serve un topic per quest, che yoga già supporta (`subscribe(routingKey, id)` / `publish(routingKey, id, payload)` ⇒ topic `questUpdated:<id>`), e che rende superfluo il `filter` nel resolver. **Non** avviare il change stream al primo subscriber: il cursore si apre in modo asincrono (Pitfall 9) e un update fra lo snapshot e l'apertura andrebbe perso, rompendo D-03. Lo stream resta sempre aperto; si salta solo la rilettura.
**Fix:**

```ts
// src/pubsub.module.ts
export const SUBSCRIBER_REGISTRY = 'SUBSCRIBER_REGISTRY';

// un listener per subscription (yoga crea una closure per ogni subscribe): il conteggio per topic dice chi ascolta
export class SubscriberRegistry extends EventTarget {
    private readonly listeners = new Map<string, Set<unknown>>();

    addEventListener(type: string, listener: EventListenerOrEventListenerObject | null, options?: AddEventListenerOptions | boolean): void {
        super.addEventListener(type, listener, options);
        if (!listener) return;
        (this.listeners.get(type) ?? this.listeners.set(type, new Set()).get(type))!.add(listener);
    }

    removeEventListener(type: string, listener: EventListenerOrEventListenerObject | null, options?: EventListenerOptions | boolean): void {
        super.removeEventListener(type, listener, options);
        this.listeners.get(type)?.delete(listener);
    }

    hasSubscribers(topic: string): boolean {
        return (this.listeners.get(topic)?.size ?? 0) > 0;
    }
}

export type PubSubEvents = {
    // ...
    questUpdated: [id: string, payload: { questUpdated: Quest }];
};

const registry = new SubscriberRegistry();
providers: [
    { provide: SUBSCRIBER_REGISTRY, useValue: registry },
    { provide: PUB_SUB, useValue: createPubSub<PubSubEvents>({ eventTarget: registry }) },
],
exports: [PUB_SUB, SUBSCRIBER_REGISTRY],

// src/quests/quests.resolver.ts: niente filter
return subscribeWithSnapshot(
    this.pubSub.subscribe('questUpdated', questId),
    async () => ({ questUpdated: await this.questsService.findOne(questId) }),
);

// src/quests/quests.publisher.ts
private async publishUpdated(questId: string): Promise<void> {
    if (!this.registry.hasSubscribers(`questUpdated:${questId}`)) return;
    const questUpdated = await this.quests.findOne(questId);
    this.pubSub.publish('questUpdated', questId, { questUpdated });
}
```

Nota: `EventTarget` di Node deduplica solo coppie identiche (type, listener, capture); ogni `subscribe` di yoga crea una closure nuova, quindi il `Set` resta esatto e la `removeEventListener` allo stop lo svuota. Il topic per quest cambia il pattern rispetto a `characterUpdated`/`userUpdated` (filter): se si preferisce l'uniformità, la variante minima è contare i listener del solo topic `questUpdated` e saltare la lettura quando nessuno ascolta alcuna quest.

### IN-03: tre publisher con lo stesso scheletro e tre stili di log degli errori

**File:** `src/quests/quests.publisher.ts:35-71`, `src/quests/results/quest-results.publisher.ts:34-66`, `src/users/user-updates.publisher.ts:33-66`, `src/quests/pending-requests/pending-requests.publisher.ts:23-29`
**Issue:** `QuestsPublisher` è una copia di `QuestResultsPublisher` con pipeline, service e topic diversi (`watch` → `on('change')` → `documentIdOf` → `findOne` → `publish`; `on('error')` → log; `onModuleDestroy` → `close`). `UserUpdatesPublisher` è la stessa cosa con `fullDocument: 'updateLookup'`. Gli errori sono loggati in tre modi: `error.name` (quests, results), `error.message` (users), `codeOf(error)` (pending-requests, il più utile: espone il codice Mongo). Con la quarta copia la duplicazione vale una base comune.
**Fix:** estrarre in `src/mongo/change-stream-publisher.ts` una classe astratta che possiede stream, hook di ciclo di vita e log, lasciando alle sottoclassi solo pipeline, opzioni e `onChange`; spostare `codeOf` in `src/mongo/` e usarlo ovunque. Se si adotta WR-01, il single-flight per chiave può vivere nella base (chiave = id del documento; `PendingRequestsPublisher` usa una chiave sola).

```ts
export abstract class ChangeStreamPublisher<TDocument> implements OnModuleInit, OnModuleDestroy {
    private changeStream?: ReturnType<Model<TDocument>['watch']>;

    protected constructor(
        private readonly model: Model<TDocument>,
        private readonly pipeline: Record<string, unknown>[],
        protected readonly logger: Logger,
        private readonly options?: ChangeStreamOptions,
    ) {}

    onModuleInit(): void {
        this.changeStream = this.model.watch(this.pipeline, this.options);
        this.changeStream.on('change', (change: ChangeStreamDocument) => void this.onChange(change));
        this.changeStream.on('error', (error: unknown) =>
            this.logger.error(`Errore nel change stream: ${codeOf(error)}`),
        );
    }

    async onModuleDestroy(): Promise<void> {
        await this.changeStream?.close();
    }

    protected abstract onChange(change: ChangeStreamDocument): Promise<void>;
}
```
